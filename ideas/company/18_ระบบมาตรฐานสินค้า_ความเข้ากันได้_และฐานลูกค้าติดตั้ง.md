# ระบบมาตรฐานสินค้า ความเข้ากันได้ และฐานลูกค้าติดตั้ง

> สถานะ: **ข้อเสนอสำหรับอนาคต ยังไม่ได้พัฒนาในเกม**
>
> วันที่: 11 พฤศจิกายน 2026 · ฐานที่ตรวจ: `main` commit `34f49a0` (v1.0.0 Debug & 7-Expert Audit)
>
> ชื่อ field, event และสูตรใหม่ในเอกสารนี้เป็นข้อเสนอ ไม่ใช่ API ที่มีอยู่แล้ว ตัวเลขเป็นค่าตั้งต้นสำหรับทดลองและต้องตรวจสมดุลด้วย simulation ก่อนใช้งานจริง

## ข้อกำหนดร่วม

- NPC และ CEO ตัดสินใจเอง ผู้เล่นติดตามเวลา แผนที่ ข้อมูล และเหตุผลการตัดสินใจ ไม่ต้องกดบริหารงานประจำ
- ขยายข้อมูลภายนอก `human-core.js`; รักษา `CORE_LOCK.json` และสูตรแกน 14 บุคลิก / 18 ค่านิยม / 30 ความถนัด / 12 สภาพเดิม
- Simulation เป็นเจ้าของสถานะ เวลา และ RNG; UI อ่าน snapshot ผ่าน API การเปิดหน้าต่างหรือวาดภาพต้องไม่เปลี่ยนผลจำลอง
- เงินใช้สตางค์จำนวนเต็มและลงบัญชีจริง วัตถุดิบ สินค้า และเวลาทำงานมีแหล่งที่มา ไม่เพิ่มทรัพยากรหรือหักต้นทุนซ้ำ
- เก็บสถานะใหม่ใน save พร้อม validation; โหลดข้อมูลเสียต้องไม่เขียนทับเกมปัจจุบัน ไม่จำเป็นต้องทำ migration เซฟข้ามแพตช์ในช่วงพัฒนาแรกตามกฎโครงการ

## 1. จุดใหม่และความแตกต่าง

เกมมีบริษัทภายนอก ความสัมพันธ์ การซื้อขาย และระบบนิเวศ ส่วนบท 10 มีสิทธิบัตร แบรนด์ และสัญญา B2B ข้อเสนอนี้เพิ่ม **ลูกค้าที่มีระบบเดิมใช้อยู่ และตัดสินใจซื้อจากต้นทุนการเปลี่ยนระบบกับความเข้ากันได้** สินค้าราคาถูกกว่าจึงไม่จำเป็นต้องชนะเสมอ

มาตรฐานเปิดกับระบบเฉพาะมีข้อแลกเปลี่ยน ไม่มีตัวเลือกใดชนะถาวร และการเข้ากันได้ต้องตรวจตามคุณสมบัติจริง ไม่อนุมานจากความเป็นพันธมิตรของบริษัท

## 2. สิ่งที่ต้องจำลอง

| ข้อมูลใหม่ | บทบาท |
| :--- | :--- |
| `standardSpec` | กลุ่มการเชื่อมต่อ เวอร์ชัน ข้อกำหนดขั้นต่ำ สิทธิ์ใช้ และกติกาความเข้ากันได้ |
| `productCompliance` | revision ของสินค้าที่ผ่านการรับรอง พร้อมขอบเขตและผลทดสอบ |
| `installedBase` | จำนวนอุปกรณ์ลูกค้าตามรุ่น/มาตรฐาน อายุ และภาระสนับสนุน |
| `adapterRecipe` | คู่ต้นทาง/ปลายทางที่รองรับ ข้อจำกัด ประสิทธิภาพ BOM และค่าติดตั้ง |
| `migrationOffer` | ราคาอุปกรณ์ ค่าติดตั้ง เวลาหยุดงาน ฝึกอบรม และเงื่อนไขสนับสนุน |

ความเข้ากันได้มีทิศทางและระดับ: ใช้ได้เต็ม ใช้ได้บางส่วนผ่านตัวแปลง หรือใช้ไม่ได้ การรองรับ A→B ไม่ได้แปลว่ารองรับ B→A และห้ามอนุมานการรองรับต่อกันหลายทอดโดยไม่ทดสอบ

## 3. วงจรลูกค้าและบริษัท

ลูกค้าเริ่มด้วยฐานอุปกรณ์จากโลกเริ่มต้นที่ระบุที่มาชัดเจน → มีความต้องการเพิ่มหรือทดแทนของเก่า → เปรียบเทียบข้อเสนอจากหลายบริษัท → ซื้อ ส่งมอบ และติดตั้งจริง → อัปเดตฐานติดตั้ง → เกิดความต้องการบริการ/ทดแทนในอนาคต

ฝ่ายขายจัดข้อเสนอ วิศวกรเสนอการรองรับมาตรฐาน CEO เลือกลงทุนรับรอง พัฒนาตัวแปลง เปิดมาตรฐาน หรือรักษาระบบเฉพาะ บริษัทคู่แข่งมีกฎและข้อจำกัดเดียวกัน ไม่สร้างฐานลูกค้าฟรีเพื่อให้แข่งชนะ

## 4. วิธีตัดสินใจที่เสนอ

ต้นทุนรวมลูกค้าในช่วงประเมินเดียวกัน = ราคาซื้อ + ติดตั้ง + ย้ายระบบ + ฝึกอบรม + บริการคาดหมาย + ค่าเสียโอกาสหยุดงานที่ประมาณการไว้

ประโยชน์รวมพิจารณาความสามารถ คุณภาพ ความเชื่อมั่น การใช้งานร่วมกับของเดิม และทางเลือกผู้ขายในอนาคต ลูกค้าเลือกตามงบและความต้องการ ไม่เลือกจากราคาซื้อต่ำสุดอย่างเดียว

ต้นทุนคาดหมายใช้ตัดสินใจเท่านั้น รายการรับจ่ายเงินจริงเกิดตามสัญญา ห้ามเรียกเก็บ “switching cost” ลอย ๆ หากไม่มีงานหรือภาระรองรับ

ความแพร่หลายของมาตรฐานเพิ่มความน่าสนใจได้ผ่านผู้ขาย อะไหล่ และช่างที่หาได้จริง ใช้ผลตอบแทนลดลงและมีทางเลือกตัวแปลง เพื่อไม่ให้ผู้นำช่วงแรกผูกตลาดถาวรโดยอัตโนมัติ

## 5. ตัวอย่างการแข่งขัน

ลูกค้ามีเซนเซอร์มาตรฐาน A จำนวน 60 ตัว บริษัทเราเสนอรุ่น B ถูกกว่า 15% แต่เปลี่ยนทั้งหมดต้องหยุดสายผลิต คู่แข่งที่ขาย A จึงยังน่าสนใจ วิศวกรเราอาจพัฒนาตัวแปลงให้ลูกค้าเปลี่ยนทีละส่วนได้ แต่ตัวแปลงกินวัตถุดิบและมีข้อจำกัดความเร็ว

อีกกรณีบริษัทเปิดมาตรฐานของตนให้ผู้ผลิตอื่นเข้าร่วม ทำให้ตลาดใหญ่ขึ้น แต่ต้องเสียค่าทดสอบและเสียความสามารถกำหนดราคาแต่ผู้เดียว ผลลัพธ์ขึ้นกับยอดใช้งานและคุณภาพการสนับสนุนจริง

## 6. สัญญา การสนับสนุน และบัญชี

- การชนะข้อเสนอไม่เพิ่มฐานติดตั้งทันที ต้องส่งและติดตั้งสำเร็จก่อน; ยกเลิก/คืนของต้องปรับด้วยหลักฐาน
- งานบริการตามฐานลูกค้าต้องมีสัญญาและใช้แรงงาน ไม่ให้จำนวนติดตั้งกลายเป็นเงินรายวันฟรี
- อายุการสนับสนุนกำหนดตั้งแต่ขาย ไม่ยกเลิกย้อนหลังเพื่อบีบให้ลูกค้าซื้อใหม่โดยไม่มีผลต่อความสัมพันธ์และภาระสัญญา
- ค่ารับรอง ค่าลิขสิทธิ์ และตัวแปลงใช้รายการบัญชีจริง ไม่เก็บซ้ำทุกครั้งที่ตรวจ compatibility
- สินค้าที่ประกาศว่าเข้ากันได้แต่ไม่ผ่านทดสอบสร้างข้อพิพาท/งานแก้ไขตามเหตุการณ์จริง ไม่ใช้ reputation หักซ้ำกับปัญหาเดียวกันหลายระบบ

## 7. การแสดงผลและการเชื่อมซอร์ส

หน้าตลาดแสดงสัดส่วนมาตรฐานของลูกค้า ข้อเสนอชนะ/แพ้เพราะอะไร และต้นทุนเปลี่ยนผ่านที่แยกองค์ประกอบ ผู้เล่นดูแผนผัง compatibility และเปิดรายละเอียดข้อจำกัดได้

เสนอ registry ใน `data.js`; คิดข้อเสนอและ installed base ใน `sim.js`; รายได้/ค่าใช้จ่ายผ่าน `economy.js`; เปิดข้อมูลใน `api.js`; validate references และยอดติดตั้งใน `save.js` เชื่อม revision จากบท 15 เมื่อมีแล้ว หรือเริ่มด้วย revision คงที่ในรุ่นทดลอง

ใช้ยอดรวมตามกลุ่มลูกค้า × รุ่นสินค้า ไม่สร้าง NPC สำหรับผู้ใช้สินค้าแต่ละราย; ประเมินเมื่อมีข้อเสนอ การเปลี่ยนสัญญา หรือรอบตลาด ไม่ประเมินทุกคู่บริษัททุก tick

## 8. ระยะพัฒนา

รุ่นแรกมีลูกค้า B2B สามกลุ่ม สองมาตรฐาน สินค้าหนึ่งประเภท ตัวแปลงหนึ่งชนิด และการซื้อเพิ่ม/ทดแทน ระยะสองเพิ่มค่าบริการกับอายุอุปกรณ์ ระยะสามเพิ่มกลุ่มผู้ร่วมกำหนดมาตรฐานและการเปลี่ยนเวอร์ชัน

ไม่จำเป็นต้องทำระบบสิทธิบัตรใหม่ซ้ำบท 10 ให้เชื่อมค่าธรรมเนียมและสิทธิ์จากระบบเดิมเมื่อพัฒนาถึงจุดนั้น

## 9. เกณฑ์ตรวจรับเมื่อพัฒนา

- ราคาถูกกว่าอาจแพ้เพราะต้นทุนย้าย และราคาสูงกว่าอาจแพ้เมื่อคู่แข่งมีทางแปลงที่คุ้มกว่า
- ระบุความเข้ากันได้แบบมีทิศทาง เวอร์ชัน และข้อจำกัดได้ถูกต้อง
- ส่งมอบ/ติดตั้งซ้ำไม่เพิ่มฐานลูกค้าซ้ำ และคืนสินค้าปรับยอดได้โดยไม่ติดลบ
- ตัวแปลงใช้ของ เวลา และสถานีจริง ไม่มีการข้ามข้อจำกัดด้วยการซื้อชื่อสินค้าอย่างเดียว
- save/load รักษาฐานติดตั้ง ภาระสนับสนุน และข้อเสนอค้าง
- คู่แข่งกับบริษัทเราใช้หลักเดียวกัน และมีสถานการณ์ที่ผู้ตามเข้าตลาดได้โดยไม่ต้องแจกเงินหรืออุปกรณ์ฟรี
