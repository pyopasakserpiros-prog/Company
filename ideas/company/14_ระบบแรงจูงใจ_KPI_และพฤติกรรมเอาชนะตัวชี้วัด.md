# ระบบแรงจูงใจ KPI และพฤติกรรมเอาชนะตัวชี้วัด

> สถานะ: **ข้อเสนอสำหรับอนาคต ยังไม่ได้พัฒนาในเกม**
>
> วันที่: 11 พฤศจิกายน 2026 · ฐานที่ตรวจ: `main` commit `34f49a0` (v1.0.0 Debug & 7-Expert Audit)
>
> ชื่อ field, event และสูตรใหม่ในเอกสารนี้เป็นข้อเสนอ ไม่ใช่ API ที่มีอยู่แล้ว ตัวเลขเป็นค่าตั้งต้นสำหรับทดลองและต้องตรวจสมดุลด้วย simulation ก่อนใช้งานจริง

## ข้อกำหนดร่วม

- NPC และ CEO ตัดสินใจเอง ผู้เล่นติดตามเวลา แผนที่ ข้อมูล และเหตุผลการตัดสินใจ ไม่ต้องกดบริหารงานประจำ
- ขยายข้อมูลภายนอก `human-core.js`; รักษา `CORE_LOCK.json` และสูตรแกน 14 บุคลิก / 18 ค่านิยม / 30 ความถนัด / 12 สภาพเดิม
- Simulation เป็นเจ้าของสถานะ เวลา และ RNG; UI อ่าน snapshot ผ่าน API การเปิดหน้าต่างหรือวาดภาพต้องไม่เปลี่ยนผลจำลอง
- เงินใช้สตางค์จำนวนเต็มและลงบัญชีจริง วัตถุดิบ สินค้า และเวลาทำงานมีแหล่งที่มา ไม่เพิ่มทรัพยากรหรือหักต้นทุนซ้ำ
- เก็บสถานะใหม่ใน save พร้อม validation; โหลดข้อมูลเสียต้องไม่เขียนทับเกมปัจจุบัน ไม่จำเป็นต้องทำ migration เซฟข้ามแพตช์ในช่วงพัฒนาแรกตามกฎโครงการ

## 1. จุดใหม่และฐานปัจจุบัน

`sim.js` มี `updateSatisfactionAndKpi`, `career.kpiScore`, จำนวนงานสะสม โบนัส และความพึงพอใจแล้ว ส่วน `ideas` บท 01 มีรางวัลพนักงานดีเด่น ข้อเสนอนี้เพิ่ม **การปรับพฤติกรรมตามสิ่งที่บริษัทให้รางวัล** และผลที่ไม่ตั้งใจต่อแผนกอื่น ไม่ใช่การเพิ่มคะแนนหรือโบนัสอีกชุดเฉย ๆ

พนักงานอาจทำตามกติกาอย่างสุจริตแต่ผลรวมแย่ลง เช่น เลือกงานง่ายเพื่อทำยอด ไม่ควรเหมารวมการตอบสนองต่อแรงจูงใจเป็นการทุจริตทั้งหมด

## 2. ตัวชี้วัดและผลข้างเคียง

| แผนก | ตัวชี้วัดแคบ | พฤติกรรมที่อาจเกิด | ตัวถ่วงดุล |
| :--- | :--- | :--- | :--- |
| ฝ่ายขาย | จำนวนออเดอร์ | รับงานกำไรต่ำหรือชนกำลังผลิต | กำไรที่รับรู้จริงและส่งตรงเวลา |
| โรงงาน | จำนวนชิ้นเสร็จ | เลือกสินค้าง่าย เลี่ยงงานค้างยาก | งานผ่าน QC ตามลำดับความเร่งด่วน |
| QC | อัตราของเสียต่ำ | ส่งงานยากไปตรวจซ้ำไม่จบ | เวลาปล่อยงานและข้อเสียที่หลุดจริง |
| จัดซื้อ | ราคาต่อหน่วยต่ำ | ซื้อครั้งละมากจนเงินจม | เงินสด สต็อกค้าง และความน่าเชื่อถือผู้ขาย |
| ฝ่ายบุคคล | ปิดตำแหน่งเร็ว | รับคนเร็วโดยไม่ดูความเหมาะสม | การคงอยู่และผลงานหลังเริ่มงาน |

ทุกพฤติกรรมต้องเป็นทางเลือกที่ทำได้จริงใน simulation ไม่มีการเพิ่มจำนวนงานหรือยอดขายปลอมเพื่อให้เกิดดราม่า

## 3. ข้อมูลที่เสนอ

- `metricPolicy`: เวอร์ชัน นโยบายรายแผนก น้ำหนัก เป้าหมาย รอบประเมิน และวันที่เริ่มมีผล
- `metricWindow`: ผลในช่วงเวลาเดียวกัน แยกงานที่มีสิทธิ์ได้รับ งานที่ได้ทำ และผลกระทบปลายทาง
- `incentiveExpectation`: สิ่งที่พนักงานคาดว่าจะได้จากโบนัส/ชื่อเสียง ไม่ใช่ยอดเงินจริง
- `metricEvidence`: อ้างอิงออเดอร์ งาน QC หรือใบซื้อที่สร้างคะแนน และรายการปรับปรุงแบบ append-only
- `policyReview`: เหตุผลทบทวน ผลเปรียบเทียบ และวันเริ่มใช้กติกาใหม่

ไม่เปลี่ยนความหมายของ `career.kpiScore` เดิมโดยเงียบ ๆ หากใช้คะแนนใหม่ให้แสดงชื่อและเวอร์ชันชัดเจน

## 4. การเลือกงานและการเรียนรู้

แนวคิดการให้คะแนนทางเลือก: `utility = jobFit + expectedReward + teamBenefit - effortCost - downstreamRisk` ทุกเทอมต้อง normalize ให้อยู่บนสเกลที่เทียบกันได้ก่อนรวม

น้ำหนักเปลี่ยนตามค่านิยมเดิม สภาพปัจจุบัน และประสบการณ์ผลตอบแทนที่ผ่านมา การร่วมมือกับเพื่อนยังมีคุณค่าในตัวเอง คนที่ไม่ได้โบนัสจึงยังช่วยงานได้ ไม่กำหนดว่า NPC ทุกคนต้องพยายามเอาชนะระบบ

คะแนนผลงานแบบสมดุลตัวอย่าง = ผลผลิตผ่านเกณฑ์ 35% + คุณภาพ 25% + ความตรงเวลา 25% + ความร่วมมือ 15% ทั้งหมดเป็นเพียงค่าเริ่มต้น ผลผลิตนับตามโอกาสและงานที่มอบหมาย แยกเงื่อนไขทรัพยากรไม่พร้อมออกจากความรับผิดของบุคคล

CEO ทบทวนรายสัปดาห์เมื่อคะแนนสูงแต่กำไร/การส่งมอบลดลง และทดลองปรับน้ำหนักทีละส่วน มีช่วงรอประเมินเพื่อไม่ให้เปลี่ยนนโยบายทุกวันตามสัญญาณรบกวน

## 5. ตัวอย่างเหตุการณ์

เดือนแรกให้รางวัลจากจำนวนผลิต โรงงานเลือกประกอบลำโพงง่ายก่อน ขณะที่ออเดอร์โคมไฟใกล้ครบกำหนดรออยู่ คะแนนโรงงานสูงแต่บริษัทเสียค่าปรับ → CEO เห็นหลักฐานและเปลี่ยนเป็นคะแนนงานผ่าน QC ที่ส่งทัน → หัวหน้าปรับคิวด้วยเหตุผลที่อธิบายได้

หากฝ่ายขายไม่ได้รับข้อมูลกำลังผลิตที่ถูกต้อง ให้แยกผลจากข้อมูลเก่าตามบท 13 ออกจากการตั้งใจเลือกงานเพื่อคะแนน

## 6. บัญชีและความเป็นธรรม

- คำนวณโบนัสเมื่อจบรอบเป็นรายการภาระผูกพัน/จ่ายจริงตามระบบบัญชีที่เลือก ห้ามให้ expectation กลายเป็นเงินใน wallet
- โบนัสมีเพดานงบ ไม่หักเงินเดือนย้อนหลังเพื่อแก้นโยบายผิด และไม่เปลี่ยนกติกาย้อนหลังหลัง NPC ลงมือแล้ว
- งานถูกยกเลิกหรือคืนสินค้าต้องมีหลักฐานปรับคะแนน แต่ไม่ลบประวัติเก่า
- ป้องกันวงจรช่วยกันทำงานปลอม งานซ้ำ หรือย้ายงานไปมาเพื่อปั๊มคะแนน ด้วย ID ของผลลัพธ์ที่นับได้ครั้งเดียว

## 7. หน้าผู้สังเกตและการเชื่อมซอร์ส

แสดงคะแนนคู่กับกำไร งานส่งทัน งานค้าง และต้นทุนภายนอก พร้อมป้าย “คะแนนดี แต่ผลต่อบริษัทแย่ลง” เมื่อมีหลักฐานจริง ผู้เล่นเปิดดูได้ว่าใครเปลี่ยนวิธีทำงานเพราะคาดหวังรางวัลอะไร

วาง metric definitions ใน `data.js`; เก็บหน้าต่างประเมินและเลือกงานใน `sim.js`; รายการจ่ายผ่าน `economy.js`; ส่งรายละเอียดผ่าน `api.js` และ UI ใน `debug.js` ห้ามเปลี่ยนสูตร core เพื่อทำให้คนดูเห็นแก่ตัว

## 8. ระยะพัฒนาและประสิทธิภาพ

รุ่นแรกมีฝ่ายขายกับโรงงาน สองนโยบายที่ CEO เลือกเอง ยังไม่เพิ่มการปลอมเอกสาร ระยะสองเพิ่ม QC และจัดซื้อ ระยะสามจึงเชื่อมข้อมูลไม่ครบและรางวัลบท 01

ใช้ยอดสะสมแบบ rolling buckets รายวัน เก็บ evidence สำคัญแบบจำกัด ไม่สแกนงานย้อนหลังทั้งหมดทุก tick

## 9. เกณฑ์ตรวจรับเมื่อพัฒนา

- นโยบายที่ต่างกันทำให้ทางเลือกงานต่างกันในสถานการณ์ควบคุม และอธิบายเหตุผลได้
- มีทั้งกรณี KPI ดีแต่ผลรวมแย่ และกรณีคะแนนสมดุลช่วยได้ โดยไม่รับประกันว่าแก้แล้วกำไรเพิ่มทุก seed
- งานถูกนับครั้งเดียว รอบประเมินซ้ำไม่จ่ายโบนัสซ้ำ และบัญชี/กระเป๋าเงินตรงกัน
- วันหยุด ความต้องการเข้าถึงพื้นที่ และการรอวัตถุดิบไม่ถูกตีความเป็นผลงานต่ำโดยอัตโนมัติ
- บันทึก/โหลดกลางรอบรักษานโยบาย ช่วงประเมิน และหนี้โบนัสเดิม
