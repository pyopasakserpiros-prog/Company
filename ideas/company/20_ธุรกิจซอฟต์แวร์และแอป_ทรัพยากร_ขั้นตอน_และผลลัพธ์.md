# ธุรกิจซอฟต์แวร์และแอป: รับจ้างพัฒนา ผลิตภัณฑ์ของตนเอง และบริการสมาชิก

> สถานะ: **ข้อเสนอสำหรับอนาคต ยังไม่ได้พัฒนาในเกม**
>
> วันที่: 11 พฤศจิกายน 2026 · ฐานซอร์สที่ตรวจ: `main` commit `934a489`
>
> ID โครงสร้างข้อมูล สูตร ตัวเลข และช่วงราคาใหม่เป็นข้อเสนอเพื่อทดลองในเกม ไม่ใช่ API ปัจจุบัน ราคาตลาดจริง ประมาณการลงทุนจริง หรือผลทดสอบสมดุล

NPC/CEO เป็นผู้ลงทุน รับงาน จัดคน และดำเนินกิจการ ผู้เล่นเฝ้าดูผลและเหตุผล ขยายทักษะ/สถานะภายนอกแกนที่ล็อกไว้ ไม่แก้ `human-core.js` หรือ `CORE_LOCK.json` ทุกธุรกิจต้องใช้เงิน เวลา คน และทรัพยากรจริงใน simulation

## 1. จุดที่ขยายจากบท 11

บท 11 เสนอ software house, POS, เกมอินดี้ และ AI ไว้แล้ว รายงานนี้ขยายให้มี **ความต้องการลูกค้า ทีมงาน ขอบเขตงาน เวอร์ชัน เกณฑ์รับมอบ บริการหลังเปิดใช้ และการเลิกใช้จริง** ซอฟต์แวร์ไม่ใช่ BOM ที่กินวัตถุดิบแล้วเสกไฟล์ขายซ้ำไม่จำกัดโดยไร้ค่าใช้จ่าย

โลกเกมจำลองงานพัฒนา ไม่สร้างแอปหรือเชื่อม cloud ของจริง และไม่เรียกเก็บเงินจริง/API จริง

## 2. สามรูปแบบหารายได้

| รูปแบบ | รายได้ | ภาระและความเสี่ยง |
| :--- | :--- | :--- |
| รับจ้างตามโครงการ | งวดที่ตกลงและผ่านรับมอบ | ขอบเขตบาน งานแก้ และลูกหนี้ |
| แอปสมาชิก SaaS | รอบบิลจากลูกค้าที่ใช้งานจริง | เซิร์ฟเวอร์ support ลูกค้ายกเลิกและชำระล่าช้า |
| ไลเซนส์ติดตั้ง + บำรุงรักษา | ค่าสิทธิ์/ติดตั้ง และสัญญาดูแล | เวอร์ชันลูกค้าต่างกัน งานอัปเกรดและความเข้ากันได้ |

เริ่มจากรับจ้างขนาดเล็ก ก่อนใช้เงินสะสมสร้างแอปของตนเอง ห้ามนับเงินมัดจำทั้งหมดเป็นกำไรทันทีหรือให้การเปิดตัวสร้างลูกค้าให้อัตโนมัติ

## 3. สิ่งที่ต้องการ

- **สถานที่:** สำนักงาน โต๊ะนักพัฒนา มุมออกแบบ จุดทดสอบ และอินเทอร์เน็ต/ไฟที่มี capacity
- **ทรัพย์สิน:** คอมพิวเตอร์ อุปกรณ์ทดสอบหลายแบบ และอาจมีเซิร์ฟเวอร์บริษัท เลือกเช่า cloud แทนได้โดยเปรียบเทียบต้นทุน
- **ทีม:** ฝ่ายขาย/ผู้วิเคราะห์งาน นักออกแบบ นักพัฒนา QA และผู้ดูแลระบบ/support บริษัทเล็กใช้คนหลายบทบาทแบบแบ่งเวลาจริง
- **ทักษะ:** ใช้ registry ภายนอกแกนเดิม ตรวจทักษะเดิมก่อนเพิ่ม เช่น การพัฒนา การทดสอบ ออกแบบ วิเคราะห์ และจัดการโครงการ ความถนัดเดิมใช้ประกอบความเหมาะกับงาน
- **เงิน:** เครื่องมือ เงินเดือน ค่าเช่าและบริการ เงินหมุนระหว่างรอ milestone และงบแก้บั๊กหลังส่ง

กรอบทดลอง: ทีมเริ่ม 3–5 คน อุปกรณ์/ติดตั้งรวม 100,000–250,000 บาทเกม และเงินหมุน 60 วัน ไม่กำหนดว่าทุกตำแหน่งต้องจ้างคนใหม่ก่อนรับงานเล็ก

## 4. ทรัพยากรดิจิทัลที่เสนอ

| ID เสนอ | ประเภท | กฎใช้ |
| :--- | :--- | :--- |
| `dev_workstation` | asset ใช้ซ้ำ | หนึ่งเครื่องถูกจองโดยคนเดียวต่อช่วงเวลา |
| `test_device` | asset ใช้ซ้ำ | ระบุแพลตฟอร์ม/รุ่น ทดสอบแทนทุกอุปกรณ์ไม่ได้ |
| `compute_hour` | บริการตามใช้ | ใช้กับ build/test/ให้บริการ ไม่เป็นสินค้ากายภาพ |
| `storage_gb_day` | capacity ต่อเวลา | เก็บข้อมูลหรือ backup จ่ายตามขนาดและเวลา |
| `api_request_credit` | เครดิตบริการจำลอง | ใช้ตามคำขอ มี rate limit และหมดได้ |
| `design_asset_license` | สิทธิ์ใช้ | ใช้ซ้ำตาม license จริง ไม่หักใหม่ทุก build ถ้าสิทธิ์ยังครอบคลุม |
| `domain_subscription` | สัญญารอบเวลา | มีวันหมดอายุ ไม่ใช่ชิ้นส่วนที่กินตอนส่งงาน |
| `developer_work_minute` | เวลาแรงงาน | แข่งกับประชุม แก้บั๊ก และ support |

บท 11 มีแนวคิด compute/GPU/license เดิม ให้รวม registry และแก้หน่วยให้ชัดเมื่อพัฒนา ไม่สร้าง ID ซ้ำสำหรับบริการเดียวกัน QA certificate ต้องเกิดจากกระบวนการตรวจ ไม่ใช่ซื้อ token แล้วสินค้าปลอดภัยทันที

## 5. ตัวอย่างแอปที่บริษัทเลือกพัฒนาได้

| แอป | ลูกค้า | งานหลักและกลไกเฉพาะ | ผลลัพธ์และวิธีหารายได้ |
| :--- | :--- | :--- | :--- |
| ร้านค้า/POS | ร้านอาหารและร้านค้าปลีก | ขาย ตัดสต็อก ออฟไลน์แล้วซิงก์ | ระบบหน้าร้าน; ค่าติดตั้ง/สมาชิกรายรอบ |
| จองคิว | คลินิก ร้านบริการ ศูนย์ซ่อม | capacity รายเวลา มัดจำ ยกเลิก/no-show | ลดคิวชน; ค่าสมาชิกตามสาขา |
| วางแผนขนส่ง/TMS | บริษัทขนส่ง | จองรถ คนขับ เส้นทาง และหลักฐานส่งของ | แดชบอร์ดกองรถ; ค่าสมาชิกตามรถที่ใช้งาน |
| คลัง/WMS | คลังและ Fulfillment | ตำแหน่งสินค้า barcode และ lot | ลดงานหาของ/หยิบผิดตามประสิทธิผลที่ทดสอบ; ค่าติดตั้ง/สัญญาดูแล |
| บุคลากร/เงินเดือน | โรงงานและสำนักงาน | กะ เวลา โบนัส สิทธิ์ข้อมูล | ระบบ HR; ค่าสมาชิกตามจำนวนผู้ใช้จริง |
| จัดซื้อ/เอกสารบริษัท | บริษัทหลายแผนก | ใบขอซื้อ อนุมัติ ประวัติแก้ไข | ตรวจสอบเอกสารได้; ค่าระบบ/บริการย้ายข้อมูล |
| งานช่างภาคสนาม | ศูนย์ซ่อมและผู้รับเหมา | นัดหมาย อะไหล่ รูปหลักฐาน และงานรับมอบ | แอปช่าง; ค่าสมาชิกและติดตั้ง |
| ผู้ช่วยค้นเอกสาร AI | บริษัทที่มีคลังเอกสาร | สิทธิ์เข้าถึง ความแม่นยำ การอ้างอิง และต้นทุนคำขอ | บริการถามตอบ; ค่าสมาชิกพร้อมโควตา/ส่วนเกิน |

ตลาดของแอปทั้งแปดแยกกัน เปิดหลายตัวพร้อมกันมีต้นทุน support/roadmap ไม่ใช่ได้โบนัสซ้อนฟรี และแอป AI ต้องมีกรณีตอบไม่ได้ ไม่อ้างว่าผลถูกต้องเสมอ

## 6. ขั้นตอนธุรกิจรับจ้าง

1. **หา lead:** ฝ่ายขายเข้าหาลูกค้าจำลองที่มีปัญหา งบ และระยะเวลาชัดเจน
2. **เก็บความต้องการ:** analyst ทำรายการ use case ข้อมูลที่ต้องย้าย ระบบที่เชื่อม และเกณฑ์ยอมรับ
3. **เสนอขอบเขต/ราคา:** ประเมินงาน ความไม่แน่นอน เวลา QA support และคิวทีม ห้ามขายชั่วโมงคนเดียวซ้ำหลายโครงการ
4. **ลงสัญญา/มัดจำ:** ระบุ deliverables, milestone, สิทธิ์ผลงาน ระยะรับประกัน และเงื่อนไขเปลี่ยนงาน
5. **ออกแบบ/ต้นแบบ:** ใช้เวลาคนและรับ feedback ก่อนลงมือฟีเจอร์ใหญ่
6. **พัฒนา:** งานย่อยมี dependency และเวลาทำจริง การตัดมุมอาจสะสม technical debt โดยไม่ผูกว่าบุคลิกใดต้องสร้างบั๊กเสมอ
7. **ทดสอบ:** ครอบคลุม functional, platform, load และ permission ตามความเสี่ยง งานที่พบปัญหากลับเข้าแก้
8. **ทดลองใช้/รับมอบ:** ลูกค้าตรวจตามเกณฑ์เดิม งานนอกขอบเขตต้องผ่าน change request ไม่บังคับทีมทำฟรีทั้งหมด
9. **deploy/ย้ายข้อมูล/ฝึก:** จองเวลาและกำหนดทาง rollback เมื่อเปิดใช้ไม่สำเร็จ
10. **เก็บเงิน/ดูแล:** ออกบิลตามงานที่รับมอบ แบ่งงาน defect ในประกันออกจาก feature ใหม่ที่คิดราคาเพิ่ม

สถานะเสนอ: `discovery → contracted → designed → implementing → testing → customer_acceptance → deployed → supporting → closed` มี blocked/change_requested/cancelled และเก็บเวอร์ชันที่ลูกค้ารับมอบไว้

## 7. ขั้นตอนธุรกิจแอปสมาชิก

สำรวจตลาด → ทำ MVP ที่แก้ปัญหาชัด → ทดสอบกับกลุ่มเล็ก → เปิดสมัคร → onboarding/ย้ายข้อมูล → เริ่มคิดรอบบิล → ดูการใช้งาน/incident → แก้ปัญหาและพัฒนา → ต่ออายุหรือยกเลิก

ลูกค้าได้มาจาก lead และการยอมรับข้อเสนอ มี conversion ไม่เกินจำนวน lead และ churn ไม่เกินลูกค้าที่มีจริง ลูกค้ายกเลิกต้องหยุดสร้างบิลอนาคตตามสัญญา มีคืนเงิน/ส่งออกข้อมูลเมื่อเกี่ยวข้อง

capacity เซิร์ฟเวอร์เป็นคอขวดร่วมกับทีม support; จำนวนผู้ใช้เกิน capacity ทำให้ช้าหรือล่มตามแบบจำลอง การซื้อ server เพิ่มไม่แก้บั๊กตรรกะโดยอัตโนมัติ

## 8. รายได้ ต้นทุน และตัวอย่าง

งานรับจ้างตัวอย่างราคา 120,000 บาทเกม แบ่งมัดจำ 30% / รับมอบทดสอบ 40% / เปิดใช้ 30% ใช้เวลาแรงงานจัดสรร 60,000 บริการ cloud 5,000 และจ้างทดสอบ 10,000 เหลือส่วนเกินโครงการ 45,000 ก่อนค่าใช้จ่ายส่วนกลางและความเสี่ยงเก็บเงิน

ถ้ามีงานแก้นอกแผนต้นทุน 20,000 ส่วนเกินลดเหลือ 25,000; เก็บมัดจำแล้วแต่ยังทำไม่เสร็จไม่ใช่กำไร 36,000 บาททันที

SaaS ตัวอย่างลูกค้าจ่ายจริง 50 บัญชี × 600 บาท/รอบ 30 วัน = บิล 30,000 บาทต่อรอบ หากค่าให้บริการรวม support และแรงงานจัดสรร 22,000 เหลือ 8,000 ก่อนค่าใช้จ่ายอื่น โดยยังไม่รวมเงินลงทุนพัฒนาเริ่มต้น ห้ามรายงานว่าเป็นเงินสดรับทั้งหมดหากยังมีบิลค้าง

**ผลลัพธ์:** release ที่ใช้งานได้ สัญญาที่รับมอบ ลูกค้าจริง รายได้/ลูกหนี้ บั๊กค้าง ภาระ support และข้อมูลความพึงพอใจ แอปจะให้ผลต่อธุรกิจอื่นได้เมื่อมีผู้ใช้/การติดตั้งจริงเท่านั้น ไม่ลดต้นทุนทั่วโลกเพียงเพราะบริษัทสร้างแอปสำเร็จ

## 9. การเติบโต ความเสี่ยง และทางออก

เส้นทาง: โครงการเล็ก → ลูกค้าประจำ → โมดูลใช้ซ้ำโดยสิทธิ์อนุญาต → ผลิตภัณฑ์ของตนเอง → SaaS หลายสาขา → เชื่อมระบบหลายธุรกิจ

ความเสี่ยง: งานบาน คนลาออกก่อนส่ง ระบบลูกค้าไม่เข้ากัน ข้อมูลย้ายผิด compute แพง บั๊กหนัก และลูกค้าเลิกใช้ CEO ลดขอบเขต ขอเลื่อน จ้างช่วง หรือหยุดผลิตภัณฑ์ตามหลักฐาน ไม่เพิ่มทีมโดยไม่คิดเวลา onboarding

ปิดแอปต้องจัดการสัญญา ข้อมูล และบริการที่ขายไว้ การใช้โมดูลซ้ำต้องไม่ละเมิดสิทธิ์สัญญารับจ้างเดิม มี cost/risk ของหลายเวอร์ชันตามบท 15/18

## 10. กลไกร่วมและเกณฑ์ตรวจรับ

เสนอ `softwareProject`, `workPackage`, `release`, `defectQueue`, `customerAcceptance`, `subscription`, `serviceCapacity`, `supportTicket` ส่วน workload/ข้อมูลใหม่อยู่ใน simulation ไม่เพิ่มสูตรแกนมนุษย์

- ชั่วโมงคน/อุปกรณ์ไม่ทับ งาน blocked ไม่เดิน progress ฟรี
- รับมอบได้เมื่อผ่านเกณฑ์และเวอร์ชันตรงสัญญา; UI ไม่กดข้ามแทน NPC
- SaaS ไม่มีลูกค้าหรือยังไม่ถึงรอบบิลไม่สร้างรายได้; หยุดบริการ/คืนเงินทำตามเงื่อนไขและไม่จ่ายซ้ำ
- แยกแรงงานจัดสรรจาก payroll จริง และมัดจำจากรายได้ตามนโยบายบัญชีที่กำหนด
- save/load กลาง deploy กลางรอบบิล และกลางแก้บั๊กให้ผลเหมือนเดิม
- การเปิดใช้แอปภายในบริษัทหักต้นทุนจริง แต่ไม่สร้างรายได้ภายนอกจากการซื้อบริการตนเอง
