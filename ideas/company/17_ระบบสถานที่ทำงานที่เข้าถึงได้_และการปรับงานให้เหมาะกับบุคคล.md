>

## ข้อกำหนดร่วม

- NPC และ CEO ตัดสินใจเอง ผู้เล่นติดตามเวลา แผนที่ ข้อมูล และเหตุผลการตัดสินใจ ไม่ต้องกดบริหารงานประจำ
- ขยายข้อมูลภายนอก `human-core.js`; รักษา `CORE_LOCK.json` และสูตรแกน 14 บุคลิก / 18 ค่านิยม / 30 ความถนัด / 12 สภาพเดิม
- Simulation เป็นเจ้าของสถานะ เวลา และ RNG; UI อ่าน snapshot ผ่าน API การเปิดหน้าต่างหรือวาดภาพต้องไม่เปลี่ยนผลจำลอง
- เงินใช้สตางค์จำนวนเต็มและลงบัญชีจริง วัตถุดิบ สินค้า และเวลาทำงานมีแหล่งที่มา ไม่เพิ่มทรัพยากรหรือหักต้นทุนซ้ำ
- เก็บสถานะใหม่ใน save พร้อม validation; โหลดข้อมูลเสียต้องไม่เขียนทับเกมปัจจุบัน ไม่จำเป็นต้องทำ migration เซฟข้ามแพตช์ในช่วงพัฒนาแรกตามกฎโครงการ

## 1. จุดใหม่และหลักการ

บท 01 มีสวัสดิการและโต๊ะสุขภาพ บท 03/10 มีความปลอดภัย ส่วนเกมมีความถนัด สภาพ และเส้นทางเดินแล้ว ข้อเสนอนี้เพิ่ม **ความสัมพันธ์ระหว่างความต้องการเฉพาะบุคคล งาน และสภาพพื้นที่** ให้การจัดสถานที่เปิดโอกาสให้คนใช้ความสามารถได้จริง

ความพิการหรือความต้องการการช่วยเหลือไม่ใช่คะแนนฝีมือต่ำ ไม่กำหนดให้ลดสติปัญญา บุคลิก หรือค่าความถนัดทุกด้าน และไม่เพิ่มมิติใหม่ในแกนที่ล็อกไว้

## 2. ประเภทความต้องการและการปรับพื้นที่

| ความต้องการ | สิ่งปรับได้ | ผลเชิงกลไก |
| :--- | :--- | :--- |
| เดินทางผ่านระดับต่างกัน | ทางลาด ประตูกว้าง ทางเดินไม่กีดขวาง | เปิดเส้นทางไปสถานีจริง |
| ต้องการลดสิ่งรบกวน | ห้องเงียบ แผงซับเสียง เวลางานที่เหมาะสม | ลดผลรบกวนเฉพาะบริบท |
| ต้องการอ่านข้อมูลชัด | หน้าจอขยาย ตัวอักษร/สัญลักษณ์คู่สี เครื่องมืออ่าน | เข้าถึงคำสั่งงานโดยมีเวลาประมวลผลที่เหมาะสม |
| ต้องการปรับท่าทางทำงาน | โต๊ะปรับระดับ เก้าอี้ เครื่องมือช่วยจับ | ทำงานที่สถานีนั้นได้อย่างปลอดภัยและต่อเนื่อง |

ควรออกแบบ UI เกมให้เข้าถึงได้ด้วย เช่น ไม่ใช้สีอย่างเดียวบอกสถานะ โดยแยกออกจากโบนัสในโลกจำลอง ผู้เล่นไม่ต้องซื้ออัปเกรดในเกมเพื่ออ่าน UI ได้

## 3. ข้อมูลที่เสนอ

- `accessNeeds`: ความต้องการรายบุคคล ขอบเขตงานที่เกี่ยวข้อง และสถานะยืนยัน ไม่ใช้การวินิจฉัยโรคเป็นสูตรการเล่น
- `stationCapabilities`: ความกว้าง ทางเข้า ระดับเสียง แสง และอุปกรณ์ช่วยของแต่ละสถานี
- `routeRequirements`: ข้อจำกัดทางผ่านและค่าเดินทางของตัวละคร โดยอ้างอิงกราฟเส้นทางเดิม
- `accommodationRequest`: ผู้ร้องขอ สิ่งกีดขวาง ทางเลือก งบ ผู้รับผิดชอบ และการติดตามผล
- `adjustmentJob`: งานติดตั้ง อุปกรณ์ เวลาปิดพื้นที่ และค่าใช้จ่ายจริง

ต้องใช้กฎเดียวกับทุกคนเมื่อบริบทเหมือนกัน และจำกัดการแสดงรายละเอียดส่วนบุคคลตามความจำเป็นในหน้าตัวละคร ไม่ใช้ป้ายล้อเลียนหรือจัดระดับคุณค่าของคน

## 4. วงจรการตัดสินใจ

NPC พบสิ่งกีดขวาง → ขอปรับพื้นที่หรือแจ้งหัวหน้า → ฝ่ายบุคคล/อาคารประเมินร่วมกับบุคคลนั้น → CEO เลือกจัดหา ปรับสถานี ย้ายงานที่เหมาะ หรือจัดทางเลือกชั่วคราว → ติดตั้งและติดตามว่าปัญหาหายจริงหรือไม่

บริษัทเล็กเริ่มจากการย้ายโต๊ะหรือปรับทางเดินได้ ไม่บังคับซื้ออาคารใหม่ราคาแพงทุกครั้ง การจัดคนเข้าทำงานประเมินฝีมือและความต้องการของงาน โดยใช้สภาพแวดล้อมหลังการปรับที่เป็นไปได้มาพิจารณา

ข้อจำกัดความปลอดภัยเป็น hard constraint ส่วนความสะดวกกับความเหนื่อยเป็น soft cost ห้ามอนุญาตทางอันตรายเพียงเพราะเป็นเส้นทางสั้นที่สุด และห้ามย้ายคนไปงานที่ตนทำไม่ได้เพื่อให้คำร้องหายจากรายการ

## 5. ตัวอย่างเรื่องราว

นักวิเคราะห์มีฝีมือสูงแต่ห้องทำงานติดเครื่องจักรเสียงดัง ทำให้ต้องพักบ่อย หัวหน้าทดลองย้ายไปห้องเงียบ ผลงานต่อชั่วโมงดีขึ้นโดยระดับทักษะเดิมไม่เปลี่ยน ต่อมาคนอื่นใช้ห้องนั้นอ่านแบบยากได้ด้วย

อีกกรณีเจ้าหน้าที่คลังใช้รถเข็นและไปสถานีรับของไม่ได้ หลังปรับทางเดินกับโต๊ะรับของ คนเดิมสามารถทำหน้าที่ได้ ไม่ใช่ได้รับโบนัสความฉลาดจากทางลาด

## 6. เศรษฐกิจและผลต่อระบบเดิม

ค่าใช้จ่ายมีทั้งวัสดุ ติดตั้ง บำรุงรักษา และเวลาปิดสถานี การปรับทางเดินมีผลต่อ topology จริง บางทางเลือกใช้พื้นที่มากขึ้นจึงต้องแลกกับความจุ ไม่สร้างผลบวกทุกมิติโดยไม่มีต้นทุน

ผลวัดรวมความปลอดภัย การทำงานได้จริง ความพึงพอใจ และการคงอยู่ของพนักงาน ไม่ตัดสินคุณค่าการเข้าถึงด้วยกำไรอย่างเดียว การปรับที่จำเป็นควรเป็นมาตรฐานพื้นฐานของบริษัทที่ดี ไม่ใช่รางวัลเฉพาะคนผลงานสูง

KPI บท 14 ต้องไม่นับเวลารอปรับสถานีเป็นความขี้เกียจ และไม่หักโบนัสเพราะเส้นทางที่บริษัทออกแบบให้เข้าถึงไม่ได้

## 7. การเชื่อมซอร์สและประสิทธิภาพ

ใช้ metadata ภายนอก profile ใน `data.js`/`sim.js`; `layout.js` ตรวจทางผ่านและสถานี; `campus-render.js` แสดงทางลาด/โต๊ะจริง; `api.js` อธิบายสิ่งกีดขวาง; `save.js` ตรวจ references และเส้นทาง

cache เส้นทางตาม access class และ layout revision แทนหาทางใหม่ทุก tick สำหรับทุก NPC ต้อง invalidate เมื่อก่อสร้างหรือย้ายสิ่งกีดขวาง และไม่แชร์ cache ระหว่างคนที่มีข้อจำกัดต่างกันโดยผิดเงื่อนไข

## 8. การพัฒนาทีละระยะ

รุ่นแรกมีความต้องการด้านทางผ่านหนึ่งแบบกับระดับเสียงหนึ่งแบบ สถานีปรับได้สองชนิด และคำร้องอัตโนมัติ ระยะสองเพิ่มเครื่องมืออ่านและโต๊ะ ระยะสามเพิ่มการประเมินพื้นที่เชิงรุกก่อนรับคน โดยไม่สร้างระบบคัดทิ้งผู้สมัครจากความต้องการของเขา

## 9. เกณฑ์ตรวจรับเมื่อพัฒนา

- เส้นทางที่เข้าถึงไม่ได้ต้องถูกตรวจพบและมีเหตุผลชัดเจน ไม่ให้ NPC เดินทะลุหรือค้างโดยไร้สถานะ
- ติดตั้งแล้วเส้นทาง/การใช้สถานีเปลี่ยนจริง คนที่ไม่เกี่ยวข้องไม่รับโบนัสทักษะฟรี
- คนสองคนที่ฝีมือเท่ากันและเข้าถึงสถานีได้เท่ากันต้องไม่ถูกลงโทษเพียงเพราะป้าย metadata
- ค่าใช้จ่ายและทรัพยากรติดตั้งถูกหักครั้งเดียว การยกเลิกคืนเฉพาะส่วนยังไม่ใช้
- save/load รักษาคำร้อง งานติดตั้ง และความสามารถสถานี; กราฟเส้นทางไม่ใช้ cache เก่า
- ตรวจ UI ที่ซูมสูง มือถือ และข้อมูลที่ไม่อาศัยสีอย่างเดียว เมื่อเริ่มลงมือพัฒนา
