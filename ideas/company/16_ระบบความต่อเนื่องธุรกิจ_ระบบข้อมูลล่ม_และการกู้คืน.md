# ระบบความต่อเนื่องธุรกิจ ระบบข้อมูลล่ม และการกู้คืน

> สถานะ: **ข้อเสนอสำหรับอนาคต ยังไม่ได้พัฒนาในเกม**
>
> วันที่: 11 พฤศจิกายน 2026 · ฐานที่ตรวจ: `main` commit `34f49a0` (v1.0.0 Debug & 7-Expert Audit)
>
> ชื่อ field, event และสูตรใหม่ในเอกสารนี้เป็นข้อเสนอ ไม่ใช่ API ที่มีอยู่แล้ว ตัวเลขเป็นค่าตั้งต้นสำหรับทดลองและต้องตรวจสมดุลด้วย simulation ก่อนใช้งานจริง

## ข้อกำหนดร่วม

- NPC และ CEO ตัดสินใจเอง ผู้เล่นติดตามเวลา แผนที่ ข้อมูล และเหตุผลการตัดสินใจ ไม่ต้องกดบริหารงานประจำ
- ขยายข้อมูลภายนอก `human-core.js`; รักษา `CORE_LOCK.json` และสูตรแกน 14 บุคลิก / 18 ค่านิยม / 30 ความถนัด / 12 สภาพเดิม
- Simulation เป็นเจ้าของสถานะ เวลา และ RNG; UI อ่าน snapshot ผ่าน API การเปิดหน้าต่างหรือวาดภาพต้องไม่เปลี่ยนผลจำลอง
- เงินใช้สตางค์จำนวนเต็มและลงบัญชีจริง วัตถุดิบ สินค้า และเวลาทำงานมีแหล่งที่มา ไม่เพิ่มทรัพยากรหรือหักต้นทุนซ้ำ
- เก็บสถานะใหม่ใน save พร้อม validation; โหลดข้อมูลเสียต้องไม่เขียนทับเกมปัจจุบัน ไม่จำเป็นต้องทำ migration เซฟข้ามแพตช์ในช่วงพัฒนาแรกตามกฎโครงการ

## 1. สิ่งที่เพิ่มจากไอเดียเดิม

บท 03 มีไฟดับและภัยพิบัติ บท 11 มี cybersecurity/PenTest ในสายพัฒนาซอฟต์แวร์ ข้อเสนอนี้จำลอง **บริษัทใช้ระบบข้อมูลทำงานอย่างไรเมื่อระบบนั้นเสีย และฟื้นกลับมาอย่างไร** เช่น ฐานสต็อกใช้งานไม่ได้ เครื่องเซิร์ฟเวอร์ขัดข้อง หรือเหตุการณ์ความปลอดภัยเชิงนามธรรม

ไม่ใช้เครือข่ายจริง ไม่แตะไฟล์ save ของผู้เล่น และไม่จำลองคำสั่งโจมตีจริง ความเสียหายทั้งหมดเกิดเฉพาะข้อมูลเหตุการณ์ในโลกเกม

## 2. ระบบที่พึ่งพากัน

| ระบบ | ถ้าใช้งานไม่ได้ | วิธีทำงานสำรอง |
| :--- | :--- | :--- |
| รับออเดอร์ | ยืนยันคำสั่งซื้อใหม่ช้า | รับคำขอรอการยืนยัน |
| คลัง | ข้อมูลพร้อมใช้ไม่สด | ตรวจนับและออกใบเบิกกระดาษ |
| ตารางผลิต | จัดคิวใหม่ยาก | ทำงานตามใบสั่งที่ปล่อยแล้ว |
| ใบส่งของ/บัญชี | ออกเอกสารและกระทบยอดช้า | สร้างรายการรอการยืนยัน |

ความสัมพันธ์ระหว่างระบบกำหนดเป็น dependency graph ตรวจวงจรก่อนใช้ ไม่ให้การล่มของระบบหนึ่งหยุดทุกอย่างโดยไร้เหตุผล

## 3. สถานะและข้อมูลที่เสนอ

- `businessService`: `id`, dependencies, `status`, เวลาที่เริ่มเสีย เจ้าของ และระดับผลกระทบ
- `recoveryPlan`: ลำดับกู้คืน คน/อุปกรณ์ที่ใช้ ทางเลือกสำรอง เป้าหมายเวลาฟื้น และอายุข้อมูลสำรองที่ยอมรับ
- `backupCheckpoint`: เวลา ขอบเขต และผลตรวจว่าสำรองใช้ได้จริง; เก็บเป็นข้อมูลจำลองแบบย่อ ไม่คัดลอกโลกเกมทุกครั้ง
- `incident`: สาเหตุ หลักฐาน ลำดับเหตุการณ์ และค่าใช้จ่ายสะสม
- `manualRecord`: รายการงานที่ทำระหว่างล่ม พร้อม operation ID และสถานะกระทบยอด

สถานะตัวอย่าง `healthy → degraded → unavailable → recovering → reconciling → healthy` อาจซ้อมกู้คืนได้โดยไม่ทำให้บริษัทหยุดจริงทั้งหมด

## 4. การตัดสินใจของ NPC

IT ประเมินอาการและความสำคัญของระบบ แยกสิ่งที่ต้องรอกู้ก่อนออกจากสิ่งที่ทำคู่ขนานได้ CEO เปรียบเทียบความเสียหายคาดหมายกับค่าระบบสำรอง การฝึก และการจ้างผู้ช่วยภายนอก

เวลาเป้าหมาย RTO คือระยะที่อยากให้กลับมาทำงานได้ ส่วน RPO คือความเก่าของข้อมูลสำรองที่ยอมรับได้ เป็นเป้าหมายการออกแบบ ไม่ใช่คำรับประกัน และไม่ใช่การย้อนเวลาโลก

ความเสี่ยงเหตุการณ์คิดเป็นรอบวัน/เหตุการณ์ ไม่สุ่มทุก tick จนความถี่เปลี่ยนตาม FPS ระบบป้องกันลดโอกาสหรือความรุนแรงได้แต่ไม่ทำให้เป็นศูนย์โดยอัตโนมัติ

## 5. การกู้คืนโดยรักษาความจริง

รายการเบิกของระหว่างล่มยังผ่านข้อจำกัดสต็อกจริง ระบบข้อมูลที่ล่มเพียงทำให้การค้นหาและยืนยันช้าลง บัญชีจำลองหลักต้องคงความถูกต้องเพื่อ audit แม้ NPC จะยังมองไม่เห็นภาพรวม

การกู้ backup คืนเฉพาะมุมข้อมูลของระบบงาน ไม่คืนเงิน วัตถุดิบ หรือคนที่ใช้ไปแล้ว นำ manual records มาเทียบ operation ID ก่อนลงทะเบียน เพื่อไม่ส่งของหรือจ่ายเงินซ้ำ ข้อมูลที่ยังพิสูจน์ไม่ได้เข้าสถานะตรวจสอบและต้องใช้เวลาคนจริง

## 6. ตัวอย่างเรื่องราว

ก่อนวันส่งของ ระบบคลังล่ม ทีมคลังใช้ใบเบิกกระดาษ โรงงานยังทำออเดอร์ที่ปล่อยแล้วได้ แต่การรับงานใหม่ช้าลง IT กู้ข้อมูลที่เก่า 4 ชั่วโมง แล้วใช้ใบเบิกเทียบรายการที่เกิดหลัง backup → บริษัทกลับมาได้โดยไม่สร้างสต็อกย้อนหลัง

เมื่อจบเหตุการณ์มีรายงานว่าเสียเวลาที่กู้ระบบเท่าไร และเสียเวลาที่ตรวจเอกสารเท่าไร ครั้งหน้าบริษัทอาจลงทุนลดอย่างหลังแทนซื้อเครื่องแพงอย่างเดียว

## 7. ต้นทุน การมองเห็น และสมดุล

ต้นทุนจริงประกอบด้วยอุปกรณ์ ค่าบริการสำรอง เวลาฝึก OT และการส่งช้าที่เกิดขึ้นจริง ห้ามหัก “รายได้ที่เสียโอกาส” เป็นเงินสดอีกครั้ง; แสดงเป็นตัวชี้วัดประมาณการแยกจากบัญชี

UI แสดงสถานะบริการ คิวกู้คืน ความพร้อมแผนสำรอง และเส้นเวลา โดยป้าย “สำรองแล้ว” ต้องแยกจาก “ทดสอบกู้คืนแล้ว” ไม่ให้ผู้เล่นต้องกดแก้ปัญหา IT ด้วยตนเอง

ต้นเกมใช้เจ้าหน้าที่ธุรการหรือผู้ขายบริการภายนอกแทนแผนก IT เต็มรูปแบบได้ และมีมาตรการราคาต่ำเพื่อไม่ให้เหตุการณ์แรกทำให้แพ้โดยไร้ทางเลือก

## 8. จุดเชื่อมและการพัฒนาทีละระยะ

เสนอ service/incident registry ใน `data.js`; การเปลี่ยนสถานะและงานกู้ใน `sim.js`; ค่าใช้จ่ายใน `economy.js`; `save.js` ตรวจ dependency และรายการที่ค้าง; `api.js` กับ `debug.js` แสดงผล

รุ่นแรกมีระบบคลังหนึ่งระบบ สาเหตุเครื่องเสีย การตรวจนับด้วยมือ และกู้ข้อมูล ระยะสองเพิ่ม dependency กับการซ้อม ระยะสามค่อยเพิ่มเหตุการณ์ความปลอดภัยแบบนามธรรมและเชื่อมรายงานบท 13

## 9. เกณฑ์ตรวจรับเมื่อพัฒนา

- ล่มแล้วงานที่พึ่งบริการนั้นช้าลงจริง แต่งานที่เป็นอิสระยังเดินต่อได้
- กู้ข้อมูลเก่าไม่ย้อน clock และไม่คืนสินค้าหรือเงินที่ใช้แล้ว
- operation ID เดิม reconcile ได้ครั้งเดียว แม้กู้ซ้ำหรือบันทึก/โหลดกลางเหตุการณ์
- recovery plan ที่ลงทุนต่างกันมีผลต่อเวลาหยุดและต้นทุนที่วัดได้
- เปลี่ยนความเร็วเกมหรือเปิดหน้าจอเพิ่มไม่เปลี่ยนความถี่เหตุการณ์ต่อวัน
- หลังกลับ healthy ไม่มีงานผูกกับบริการที่หายไป และ audit บัญชี/สินค้าผ่าน
