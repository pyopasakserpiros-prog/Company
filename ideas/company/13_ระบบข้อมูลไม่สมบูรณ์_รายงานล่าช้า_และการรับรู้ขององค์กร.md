# ระบบข้อมูลไม่สมบูรณ์ รายงานล่าช้า และการรับรู้ขององค์กร

> สถานะ: **ข้อเสนอสำหรับอนาคต ยังไม่ได้พัฒนาในเกม**
>
> วันที่: 11 พฤศจิกายน 2026 · ฐานที่ตรวจ: `main` commit `34f49a0` (v1.0.0 Debug & 7-Expert Audit)
>
> ชื่อ field, event และสูตรใหม่ในเอกสารนี้เป็นข้อเสนอ ไม่ใช่ API ที่มีอยู่แล้ว ตัวเลขเป็นค่าตั้งต้นสำหรับทดลองและต้องตรวจสมดุลด้วย simulation ก่อนใช้งานจริง

## ข้อกำหนดร่วม

- NPC และ CEO ตัดสินใจเอง ผู้เล่นติดตามเวลา แผนที่ ข้อมูล และเหตุผลการตัดสินใจ ไม่ต้องกดบริหารงานประจำ
- ขยายข้อมูลภายนอก `human-core.js`; รักษา `CORE_LOCK.json` และสูตรแกน 14 บุคลิก / 18 ค่านิยม / 30 ความถนัด / 12 สภาพเดิม
- Simulation เป็นเจ้าของสถานะ เวลา และ RNG; UI อ่าน snapshot ผ่าน API การเปิดหน้าต่างหรือวาดภาพต้องไม่เปลี่ยนผลจำลอง
- เงินใช้สตางค์จำนวนเต็มและลงบัญชีจริง วัตถุดิบ สินค้า และเวลาทำงานมีแหล่งที่มา ไม่เพิ่มทรัพยากรหรือหักต้นทุนซ้ำ
- เก็บสถานะใหม่ใน save พร้อม validation; โหลดข้อมูลเสียต้องไม่เขียนทับเกมปัจจุบัน ไม่จำเป็นต้องทำ migration เซฟข้ามแพตช์ในช่วงพัฒนาแรกตามกฎโครงการ

## 1. จุดใหม่และความสนุก

เกมมีสถานะจริงของคลัง งาน เงิน และบุคลากร ส่วน `ideas` บท 02 และ 10 มีข่าวลือกับการเมืองในออฟฟิศแล้ว ข้อเสนอนี้เพิ่ม **ความแตกต่างระหว่างความจริงกับข้อมูลที่ผู้ตัดสินใจได้รับ** ในงานประจำ เช่น รายงานคลัง ใบส่งของ และประมาณการกำลังผลิต ข่าวลืออาจใช้ช่องทางเดียวกันในอนาคต แต่ไม่จำเป็นต่อรุ่นแรก

บริษัทพลาดได้แม้มีพนักงานเก่ง เพราะรายงานมาช้า ไม่ครบ หรือใช้ข้อมูลคนละเวลา ผู้เล่นตามรอยเหตุการณ์ได้ว่าการตัดสินใจนั้นสมเหตุสมผลเพียงใดเมื่อเทียบกับข้อมูลที่ NPC มีขณะนั้น

## 2. วงจรและผู้รับผิดชอบ

1. แผนกเจ้าของงานบันทึกข้อสังเกตจากเหตุการณ์จริง เช่น รับของ ผลิตสำเร็จ หรือเครื่องหยุด
2. ผู้รับผิดชอบรวบรวมและส่งรายงานตามรอบ โดยมีต้นทุนเวลาและคิวงาน
3. ผู้รับอ่าน ตรวจสอบ และอาจขอข้อมูลยืนยันก่อนใช้ตัดสินใจ
4. ข้อมูลใหม่แทนข้อมูลเก่าเฉพาะเมื่อมีหลักฐานและเวลาที่ใหม่กว่า; รายงานที่เพิ่งส่งถึงอาจมีเนื้อหาเก่า
5. เมื่อผลจริงปรากฏ ระบบเทียบคำคาดการณ์กับผลลัพธ์ แล้วปรับวิธีรายงานหรือความเชื่อมั่นต่อแหล่งข่าว

ฝ่ายคลังรับผิดชอบยอดคงเหลือ ฝ่ายขายคาดการณ์คำสั่งซื้อ โรงงานประเมินกำลังผลิต และ CEO ประสานภาพรวม การรับรู้ไม่ใช่สิทธิ์แก้ยอดจริง

## 3. ข้อมูลที่เสนอ

| ข้อมูล | เนื้อหาและกฎ |
| :--- | :--- |
| `report` | `id`, `topic`, `sourceId`, `recipientUnitId`, `observedAt`, `sentAt`, `arrivedAt`, `value`, `unit`, `confidence`, `evidenceIds` |
| `beliefByUnit` | ค่าที่แผนกเชื่อ ช่วงค่าที่เป็นไปได้ เวลาที่ข้อมูลถูกสังเกต และรายงานอ้างอิง |
| `reportQueue` | รายงานที่รอจัดทำ ส่งถึง หรืออ่านแล้ว พร้อมสถานะที่ชัดเจน |
| `decisionEvidence` | สำเนาข้อมูลที่ใช้ตัดสินใจ ณ เวลานั้น เพื่อไม่ให้หลักฐานเปลี่ยนย้อนหลัง |

แยกศูนย์จริงออกจากไม่ทราบค่า ใช้หน่วยเดียวกันในการรวมรายงาน เช่น ชิ้นและนาที ห้ามนำจำนวนที่ถูกจองไปตีความเป็นจำนวนพร้อมใช้

## 4. การตัดสินใจอัตโนมัติ

ค่าความสดใหม่ตัวอย่าง: `freshness = 2 ** (-ageMinutes / halfLifeMinutes)` โดย `halfLifeMinutes > 0` คือเวลาที่ทำให้น้ำหนักความสดใหม่เหลือครึ่งหนึ่ง หัวข้อสต็อกเคลื่อนไหวเร็วควรมีช่วงนี้สั้นกว่าข้อมูลอาคาร

ความเชื่อมั่นใช้งาน = ความเชื่อมั่นรายงาน × ความสดใหม่ × ความน่าเชื่อถือของแหล่งข่าว และ clamp อยู่ระหว่าง 0–1 ค่านี้บอกความมั่นใจ ไม่ได้รับประกันว่าข่าวถูกจริง

ฝ่ายขายเปรียบเทียบทางเลือก รับงาน / ขอข้อมูล / ชะลอ โดยพิจารณากำไรคาดหมาย ความเสี่ยงส่งช้า และต้นทุนเสียโอกาส หากข้อมูลสำคัญไม่พอให้มีทางเลือกรอหรือยืนยันเสมอ บุคลิกและความถนัดเดิมมีผลต่อการประเมิน แต่ไม่บังคับให้คนใดผิดเสมอ

**ข้อจำกัดสำคัญ:** บัญชี การหักวัตถุดิบ และการอนุมัติธุรกรรมต้องตรวจสถานะจริงเสมอ ความเชื่อผิดทำให้วางแผนผิดได้ แต่ห้ามทำให้สต็อกติดลบหรือใช้เงินที่ไม่มีอยู่

## 5. ตัวอย่างเรื่องราว

08:00 คลังรายงาน PCB พร้อมใช้ 80 ชิ้น → 09:00 โรงงานใช้ไป 60 ชิ้น → 09:10 ฝ่ายขายยังเห็นรายงานเก่าและรับงานเพิ่ม → 09:15 ตรวจจองจริงพบของไม่พอ จึงสร้างคำขอจัดซื้อและประเมินส่งล่าช้า → 10:00 รายงานใหม่มาถึง CEO จัดรอบรายงานใหม่ให้เร็วขึ้น

บันทึกสาเหตุควรระบุ “ใช้รายงานอายุ 70 นาที” แทนการสรุปว่า “ฝ่ายขายโง่” ความผิดพลาดมาจากระบบการทำงานด้วย

## 6. ต้นทุน สมดุล และการแสดงผล

- รายงานถี่ใช้เวลาธุรการและเวลางานต้นทาง; การลงทุนระบบข้อมูลลดความล่าช้าแต่มีค่าติดตั้งและบำรุงรักษา
- ไม่เพิ่มค่าปรับสมมติจากความเชื่อผิดโดยตรง เงินเสียเกิดจากการส่งช้า สั่งด่วน หรือเหตุการณ์จริงตามสัญญา
- หน้าผู้สังเกตมีสองมุม: สถานะจริง และสิ่งที่แผนกเชื่อ พร้อมเวลา/แหล่งข่าว/เหตุผล ห้ามเปิด UI แล้วส่งข่าวให้ NPC อัตโนมัติ
- มีแผนภาพเส้นทางรายงานและตัวกรองเฉพาะเหตุการณ์สำคัญ ไม่แสดงทุกข้อความจนอ่านไม่ไหว

## 7. การเชื่อมกับซอร์สและขอบเขตรุ่นแรก

เสนอ registry หัวข้อและรอบรายงานใน `data.js`; คิวและ beliefs ใน `sim.js`; หลักฐานการตัดสินใจใน `api.js`; ตรวจ save ใน `save.js`; หน้าตรวจใน `debug.js` โดยไม่เปลี่ยนแกนมนุษย์

รุ่นแรกจำลองเฉพาะข้อมูล PCB ระหว่างคลังกับฝ่ายขาย สองรอบรายงาน ไม่มีการโกหก ไม่มีอีเมลจริง ระยะถัดไปเพิ่มกำลังผลิต กระแสเงินสด และเชื่อมเหตุการณ์ข่าวลือจากบท 02

เก็บค่าล่าสุดตามแผนกและหัวข้อ ไม่เก็บสำเนาโลกให้ NPC ทุกคน; จำกัดประวัติรายงานและเก็บ decision evidence เฉพาะการตัดสินใจสำคัญเพื่อรองรับ 500 NPC

## 8. เกณฑ์ตรวจรับเมื่อพัฒนา

- seed และคำสั่งเหมือนกันให้รายงานกับผลจำลองเหมือนกัน รวมถึง save/load กลางคิว
- รายงานเก่าที่ถึงทีหลังไม่ทับข้อสังเกตใหม่; ข่าวซ้ำไม่ทำให้บันทึกซ้ำ
- มีสถานการณ์ที่ความเชื่อกับความจริงต่างกัน และยืนยันได้ว่า NPC ใช้ข้อมูลที่ตนมี
- ความเชื่อผิดไม่สร้างของ เงิน หรือทำให้ข้อจำกัดจองทรัพยากรเสีย
- ปิดระบบแล้วกลับสู่พฤติกรรมฐานตามขอบเขตที่กำหนด; รายงานถี่มีทั้งต้นทุนและประโยชน์ที่วัดได้
- โหลดใหม่รักษาคิวและหลักฐานเดิม; snapshot ซ้ำไม่เปลี่ยนเวลา/RNG

## 9. เชื่อมกับไอเดียอื่น

ใช้เป็นฐานข้อมูลที่ระบบ KPI ในบท 14 ตรวจเทียบกับหลักฐานจริง และรับผลจากการทำงานเอกสารระหว่างระบบล่มในบท 16 โดยเริ่มพัฒนาแยกกันได้
