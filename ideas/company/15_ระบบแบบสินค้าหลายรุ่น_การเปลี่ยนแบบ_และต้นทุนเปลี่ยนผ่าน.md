# ระบบแบบสินค้าหลายรุ่น การเปลี่ยนแบบ และต้นทุนเปลี่ยนผ่าน

> สถานะ: **ข้อเสนอสำหรับอนาคต ยังไม่ได้พัฒนาในเกม**
>
> วันที่: 11 พฤศจิกายน 2026 · ฐานที่ตรวจ: `main` commit `34f49a0` (v1.0.0 Debug & 7-Expert Audit)
>
> ชื่อ field, event และสูตรใหม่ในเอกสารนี้เป็นข้อเสนอ ไม่ใช่ API ที่มีอยู่แล้ว ตัวเลขเป็นค่าตั้งต้นสำหรับทดลองและต้องตรวจสมดุลด้วย simulation ก่อนใช้งานจริง

## ข้อกำหนดร่วม

- NPC และ CEO ตัดสินใจเอง ผู้เล่นติดตามเวลา แผนที่ ข้อมูล และเหตุผลการตัดสินใจ ไม่ต้องกดบริหารงานประจำ
- ขยายข้อมูลภายนอก `human-core.js`; รักษา `CORE_LOCK.json` และสูตรแกน 14 บุคลิก / 18 ค่านิยม / 30 ความถนัด / 12 สภาพเดิม
- Simulation เป็นเจ้าของสถานะ เวลา และ RNG; UI อ่าน snapshot ผ่าน API การเปิดหน้าต่างหรือวาดภาพต้องไม่เปลี่ยนผลจำลอง
- เงินใช้สตางค์จำนวนเต็มและลงบัญชีจริง วัตถุดิบ สินค้า และเวลาทำงานมีแหล่งที่มา ไม่เพิ่มทรัพยากรหรือหักต้นทุนซ้ำ
- เก็บสถานะใหม่ใน save พร้อม validation; โหลดข้อมูลเสียต้องไม่เขียนทับเกมปัจจุบัน ไม่จำเป็นต้องทำ migration เซฟข้ามแพตช์ในช่วงพัฒนาแรกตามกฎโครงการ

## 1. จุดใหม่และขอบเขต

เกมมี BOM สูตรแปรรูป วัตถุดิบ QC และออเดอร์แล้ว บท 05 กับ 11 ขยายห่วงโซ่และสินค้า ส่วนบท 10 มีงาน R&D และ RMA ข้อเสนอนี้เพิ่ม **อายุของแบบสินค้า การอนุมัติเปลี่ยนแบบ และการอยู่ร่วมกันของรุ่นเก่ากับใหม่** โดยไม่ทำให้สูตรที่แก้ใหม่เปลี่ยนออเดอร์เก่าย้อนหลัง

ความสนุกอยู่ที่เวลาตัดสินใจเปิดตัว: แบบใหม่ดีขึ้น แต่บริษัทมีเครื่องมือ สินค้าค้าง และคำสัญญากับลูกค้ารุ่นเดิมอยู่

## 2. โครงสร้างแบบและวงจรอนุมัติ

| สิ่งใหม่ | ข้อมูลหลัก |
| :--- | :--- |
| `productRevision` | `productId`, `revisionId`, BOM, routing, เกณฑ์ QC, มาตรฐานที่รองรับ, วันปล่อยใช้ |
| `engineeringChange` | ผู้เสนอ เหตุผล revision ต้นทาง/ปลายทาง ผลทดลอง ต้นทุน และผู้อนุมัติ |
| `revisionLot` | ล็อตวัตถุดิบ/WIP/สินค้า ที่มารุ่น จำนวน สถานะ และมูลค่าบัญชี |
| `changeoverJob` | เครื่องมือ คน เวลา และทรัพยากรที่ต้องใช้เพื่อเปลี่ยนสายผลิต |
| `legacySupport` | ข้อผูกพันอะไหล่ การรับประกัน และวันสิ้นสุดการสนับสนุนที่ตกลงไว้ |

ลำดับ: `draft → prototype → validated → approved → released → retired` มีทางปฏิเสธและยกเลิกก่อน release แบบที่ release แล้วแก้เนื้อหาทับไม่ได้ ต้องสร้าง revision ใหม่

## 3. วงจร NPC

วิศวกรเสนอแบบจากปัญหา QC หรือโอกาสลดต้นทุน → สร้างต้นแบบโดยใช้ของและเวลา → QC ตรวจ → จัดซื้อประเมินของค้างและเวลาหาผู้ขาย → โรงงานประเมินเปลี่ยนเครื่องมือ → ฝ่ายขายประเมินลูกค้า → CEO เลือกเปิดทันที เลื่อน หรือยกเลิก

บริษัทเล็กให้คนเดียวทำหลายหน้าที่ได้ แต่ยังต้องผ่านเกณฑ์ทดลองจริงและบันทึกเหตุผล ห้ามกำหนดตำแหน่งใหม่จนต้นเกมเดินต่อไม่ได้

## 4. เกณฑ์เลือกและผลต่อการผลิต

เปรียบเทียบทางเลือกด้วย `benefit = expectedContribution - toolingCost - trialCost - inventoryWriteDown - transitionLoss - supportReserve` ใช้ช่วงเวลาประเมินและหน่วยเงินเดียวกัน และไม่รวมต้นทุนเดียวกันซ้ำ

CEO ใช้ประมาณการตามข้อมูลที่ได้รับ ส่วนบัญชีใช้ธุรกรรมจริงเสมอ สามารถยอมรับผลตอบแทนต่ำเพื่อความปลอดภัยได้ การเปลี่ยนแบบเพื่อความปลอดภัยต้องแยกจากการลดต้นทุนทั่วไป

เมื่อรับออเดอร์ต้องระบุ revision ที่ตกลงไว้ หากลูกค้ายอมให้ใช้รุ่นเทียบเท่าให้มีรายการอนุมัติและเกณฑ์ความเข้ากันได้ชัดเจน WIP เดิมเดินต่อด้วยแบบเดิม ยกเว้นมีงาน rework ที่หักวัตถุดิบและแรงงานจริง

## 5. ตัวอย่างเรื่องราว

รุ่น A ใช้แบตเตอรี่ชนิดเดิม 1 ก้อน รุ่น B เปลี่ยนวงจรเพื่อลดต้นทุน 8% แต่ต้องเปลี่ยน jig และยังมีแบตเตอรี่เดิม 100 ก้อน CEO อาจทำ A ต่อให้ครบสัญญา แล้วจึงเปลี่ยนเป็น B แทนเปิด B ทันทีจนต้องทิ้งของเก่า

ระหว่างเปลี่ยนสายผลิต คนและสถานีถูกใช้กับงานตั้งเครื่อง ทำให้งานอื่นรอจริง เมื่อ release B ผู้เล่นเห็นป้ายรุ่นและสินค้าคงเหลือแยกกัน

## 6. กฎบัญชีและป้องกันช่องโหว่

- การย้ายสถานะวัตถุดิบ → WIP → สินค้าต้องรักษาปริมาณและมูลค่าตามวิธีประเมินต้นทุนที่กำหนด
- ของล้าสมัยมีทางใช้กับงานเดิม ขายคืน แปรใช้ หรือทิ้ง; การด้อยค่าไม่ใช่เงินสดออกซ้ำจากวันที่ซื้อ
- การซื้อเครื่องมือจ่ายจริงครั้งเดียว; ค่าเสื่อมในอนาคตห้ามถูกหักเป็นเงินสดอีกครั้ง
- แบบใหม่ไม่ทำให้สินค้าเก่าอัปเกรดฟรี หากแปลงได้ต้องมีสูตร rework และของเสีย
- การถอนแบบไม่ทำให้ภาระรับประกันหายไป; หากมี recall ให้ใช้ระบบบท 10 แทนสร้างระบบเรียกคืนซ้ำ

## 7. การเชื่อมซอร์สและ save

`data.js` เก็บ revision registry แบบ immutable; `sim.js` จัดการอนุมัติ งานทดลองและ changeover; ออเดอร์/หน่วยผลิตต้องจับ revision ตอนสร้างงาน; `save.js` ตรวจ reference และสูตร; `api.js` เปิด revision กับเหตุผลการเปลี่ยนให้ UI

นี่เป็นงาน schema ที่กระทบหลายจุด ไม่ควรเริ่มด้วยการเปลี่ยน `catalog.products[id].bom` ทับทั้งโลก สถานะเก่าที่อ้าง revision ไม่มีอยู่ต้องถูกปฏิเสธตอนโหลด

## 8. รุ่นแรกและเกณฑ์ตรวจรับ

รุ่นแรกใช้ลำโพงหนึ่งสินค้า สอง revision หนึ่งงานเปลี่ยน jig และออเดอร์รุ่นเดิมที่ค้างอยู่ ระยะสองเพิ่ม rework กับอะไหล่ ระยะสามเชื่อมมาตรฐานบท 18

- ออเดอร์เดิมใช้ BOM เดิม แม้มีการปล่อยรุ่นใหม่แล้ว
- ระหว่างเปลี่ยนเครื่องมือสถานีรับงานเกินความสามารถไม่ได้ และการยกเลิกไม่คืนวัตถุดิบที่ใช้ไปแล้ว
- save/load กลาง WIP และกลาง changeover ให้ผลต่อเนื่องเหมือนเดิม
- audit ปริมาณและบัญชีหลังด้อยค่า ขายคืน และ rework ต้องผ่าน
- มีกรณีที่เลื่อนเปิดตัวคุ้มกว่าเปิดทันที และกรณีความปลอดภัยที่ควรหยุดแบบเดิม
- ไม่เปิดให้วางขาย prototype ก่อน validation หรือให้ UI ข้ามขั้นอนุมัติเอง
