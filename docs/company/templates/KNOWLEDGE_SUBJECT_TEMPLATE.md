# เทมเพลตสร้างวิชาและความเชี่ยวชาญ NPC

ใช้ทุกครั้งที่เพิ่ม/แยก/ปรับวิชา ความรู้ หรือหลักสูตรใน Company อ่าน AGENTS.md และ [คู่มือระบบ](../LEARNED_KNOWLEDGE_SYSTEM.md) ก่อน แบบนี้เป็นสัญญาการออกแบบระยะยาว ไม่ใช่รายการแพตช์ที่ทำครั้งเดียว

## 1. ตัวตนและขอบเขต

- ID คงที่: `lower_snake_case`; ชื่อภาษาไทย; หมวด; ผู้ดูแลข้อมูล/จุดประกาศใน source
- วิชานี้สอนอะไร ทำอะไรได้ และไม่ครอบคลุมอะไร? แยกความรู้จากอาชีพ ตำแหน่ง บุคลิก และความถนัดติดตัว
- ทุกวิชาเปิดให้บุคคลเรียนได้ แม้บริษัทไม่มีงานที่ใช้ ห้ามล็อกวิชาเพียงเพราะโมเดลธุรกิจยังไม่มีในเกม; แสดงเพียงว่ายังไม่ได้ใช้ในงานบริษัท
- สิ่งที่มีอยู่แล้วใกล้เคียงอะไร? จะใช้วิชาเดิมร่วม แยกวิชา หรือสร้างใหม่ เพราะอะไร?
- ระบุธุรกิจ สินค้า กระบวนการ งานสำนักงาน/งานวิจัยที่ใช้จริง; วิชาที่บริษัทยังไม่ใช้ต้องยังเรียนได้ มี prerequisite น้ำหนักแกน ระดับ ประสบการณ์ และผลประเมินเหมือนวิชาอื่น; อย่าสร้างธุรกิจปลอมเพื่ออ้างว่าใช้แล้ว

## 2. องค์ประกอบและระดับ

- พื้นฐานเชิงทฤษฎี, ขั้นตอนปฏิบัติ, การสังเกต/วิเคราะห์, ความแม่นยำ, ความปลอดภัย/คุณภาพ และการถ่ายทอดความรู้ องค์ประกอบใดมีผลกับวิชานี้บ้าง?
- วิชาก่อนหน้าและระดับที่ต้องผ่าน ระบุเป็นกราฟไร้วงจร เช่น คณิตศาสตร์พื้นฐาน 40 → ประยุกต์ 60 → เริ่มเรียนขั้นสูง
- ความหมายระดับ 0–100: 0 ยังไม่เคยเรียน, 20 พื้นฐาน, 40 ปฏิบัติงานได้, 60 ขั้นสูง, 80 ผู้เชี่ยวชาญ, 95 เชี่ยวชาญสูง ต้องยกตัวอย่างงานที่แต่ละระดับทำได้และยังทำไม่ได้
- งานเสี่ยงหรือซับซ้อนต้องใช้ระดับใด? ระดับวิชาไม่ใช่ใบอนุญาตตามกฎหมาย/ใบรับรองของจริง และไม่เท่ากับเทคโนโลยีของบริษัท

## 3. ความเชื่อมโยง Human Core (อ่านอย่างเดียว)

- เลือกความถนัดหลายด้านจาก 30 แกนที่มีจริง พร้อมน้ำหนักรวม 1.0 และเหตุผลทีละแกน ห้ามสร้างแกนใหม่หรือเปลี่ยนสูตร core
- แยก **aptitudes** (ศักยภาพที่ใช้งานขณะนี้), **potential** (เพดานพัฒนา), **learningSpeed** (อัตราเรียน) และความรู้ที่เรียนมาแล้ว ไม่ตั้งให้พรสวรรค์สูงรู้เนื้อหาทันที
- ตัวอย่างคณิตศาสตร์: numerical .35, analytical .30, memory .20, uncertaintyReasoning .15 ส่วนงานฝีมือใช้ dexterity/precision/sensory/coordination น้ำหนักอีกชุดหนึ่ง
- อธิบายผลของพลังงาน ความเครียด ความรอบคอบ/แรงจูงใจ และประสบการณ์ อย่านับผลซ้ำกับ H.evaluateAbility โดยไม่ตั้งใจ
- สูตรในระบบปัจจุบัน: อ่าน `subjectSpec`, `subjectTalent`, `subjectPotential`, `subjectPerformance`, `learnSubject`, `ability` ใน COMPANY_SOURCE/js/sim.js ก่อนคัดตัวเลข ห้ามคัดคำอธิบายเก่าที่สูตรเปลี่ยนแล้ว

## 4. การเรียนและพัฒนา

- แหล่งความรู้: ประวัติก่อนเข้าทำงาน/ผู้สมัคร, หลักสูตรภายนอกที่จ่ายเงิน, ลงมือทำจริง, โครงการวิจัยที่มีวัตถุดิบ/ผู้ตรวจ หากเสนอพี่เลี้ยง ต้องเพิ่มเวลาและการจองตัวผู้สอนจริงก่อนอ้างว่ามีระบบนั้น
- เวลาใช้หน่วยนาที simulation; แยกชั่วโมงศึกษาออกจากชั่วโมงใช้งานจริง (`practiceMinutes`/`appliedMinutes`) อย่าให้เร่งความเร็วเกมเพิ่มความรู้ต่อหนึ่งวัน
- อัตราเรียนแต่ละช่วงระดับ, เงื่อนไขก่อนเรียน, ค่าใช้จ่ายและประเภท ledger, เพดานศักยภาพ, ข้อจำกัดชั่วโมงต่อวัน และหลักฐานก่อนเป็นผู้เชี่ยวชาญ
- คนเก่งเรียนไว/ทำงานดีขึ้นอย่างไร? คนธรรมดาพัฒนาได้แค่ไหน? ถ้าปรับความถนัดลง ต้องไม่ลบความรู้ที่สะสมแล้วโดยไม่มีเหตุ
- อธิบายเกณฑ์พัก/เรียนต่อ/เปลี่ยนแผนของ NPC เมื่อขาดเงิน เหนื่อย ไม่มีวิชาพื้นฐาน หรือผู้เชี่ยวชาญออกจากงาน

## 5. ผลต่องานและธุรกิจ

สร้างตารางอย่างน้อยดังนี้:

| งาน/สินค้า/ธุรกิจ | วิชาที่ต้องใช้ร่วม + ระดับ | คนเดียวหรือทีมร่วมกันได้ | จุดเรียกใช้ใน source | ผลที่เกิดจริง |
|---|---|---|---|---|
| ระบุรายการจริง | 1–5 วิชาหรือจำนวนที่สมเหตุผล; รวมวิชาสำนักงาน/ความปลอดภัยที่จำเป็น | ระบุผู้ทำหลัก ผู้ร่วม และผู้ตรวจอิสระ | producer → planner → gate → execution → snapshot | ความเร็ว/คุณภาพ/ของเสีย/การอนุญาต/ต้นทุน/เวลา |

- วิชาทั่วไป เช่น บัญชี ไฟฟ้า จัดซื้อ ใช้ร่วมหลายธุรกิจได้ แต่ไม่แทนสาขาเฉพาะ เช่น พัฒนาเฟิร์มแวร์ หรือทำงานปลอดเชื้อ
- แยก hard gate (ทำไม่ได้เพราะขาดความรู้ คน เครื่องมือ ทุน ใบอนุญาต หรือกระบวนการ) จาก soft decision (ทำได้แต่ผู้บริหารเลือกเก็บเงิน/ซื้อภายนอก/รอ)
- ห้ามเพิ่มความสามารถสร้างเงิน/สินค้า/ทรัพยากรโดยไม่มี input และบัญชีจริง วิชาบัญชีต้องไม่สุ่มเปลี่ยนยอด ledger เพื่อจำลองทำบัญชีผิด
- ระบุผลเมื่อคนที่รู้วิชาเดียวกันย้ายงาน ลาออก พัก หรือถูกจองในงานอื่น และอย่าให้คนเดียวถูกขายชั่วโมงซ้อนหลายธุรกิจ

## 6. ข้อมูล/API/หน้าจอ/เซฟ

ตัวอย่างโครงสร้างข้อเสนอ (ปรับให้ตรง source จริง; ไม่ใช่การเรียก API ที่มีทั้งหมด):

```json
{
  "id": "advanced_math",
  "nameTh": "คณิตศาสตร์ขั้นสูง",
  "category": "คณิตศาสตร์",
  "prerequisite": "applied_math",
  "prerequisiteLevel": 60,
  "aptitudes": {"numerical": 0.35, "analytical": 0.30, "memory": 0.20, "uncertaintyReasoning": 0.15},
  "consumers": ["งานวิเคราะห์และออกแบบระบบที่ระบุจริง"],
  "requiredLevel": 40,
  "observableEffect": "ระบุสูตร/การตัดสินใจ/ผลลัพธ์ที่ผู้เล่นตรวจได้"
}
```

- อัปเดต SUBJECTS/SUBJECT_DETAILS, prerequisites/ระดับ prerequisite, aptitude model/ข้อยกเว้น, background ผู้สมัคร และ requirements matrix ตามงาน
- snapshot ต้องบอกชื่อวิชา ระดับ ผู้รู้ วิชาที่ขาด ความเหมาะสมจากแกน และผลต่องานในภาษาที่อ่านได้ ผู้เล่นไม่จำเป็นต้องจำ ID
- เซฟต้องเก็บความรู้ ประสบการณ์ หลักสูตร โครงการ งบ วัตถุดิบ และการตรวจรับต่อเนื่อง ตรวจค่าผิดปกติ ข้อมูลอ้างอิง และการโหลดโดยไม่ทำลายโลกเดิม
- ระบุการรับเซฟเก่าที่รองรับและผลต่อออเดอร์เดิม ห้ามแปลงแต้มรวมเป็นความรู้ทุกวิชาให้พนักงานทุกคน

## 7. หลักฐานก่อนส่งมอบ

- ตรวจ schema, ID ไม่ซ้ำ, aptitude keys ถูกต้อง/น้ำหนักรวม 1, prerequisite ไม่วน, matrix อ้างวิชาที่มีจริง และทุกวิชามีผลใช้หรือเป็น prerequisite
- เปรียบเทียบพรสวรรค์สูง/ต่ำด้วยความรู้เริ่มเท่ากัน; ความรู้สูง/ต่ำด้วยแกนและสถานการณ์เท่ากัน; เหนื่อย/พร้อม; มี/ขาดเครื่องมือ
- ตรวจไม่มีพื้นฐาน/ไม่มีผู้เชี่ยวชาญ/ผู้เชี่ยวชาญลาออก, การเรียนเกินชั่วโมง, เงินไม่พอ, ผู้ตรวจซ้ำคนทำ, ต้นแบบไม่ผ่าน และ input ขาด
- ทดสอบหลาย seed/ระยะยาว, การเร่งเวลา, save/load ต่อเนื่องและข้อมูลเสีย, UI มือถือ; อ้างเฉพาะผลที่รันจริง
- อัปเดตทะเบียนวิชา, คู่มือระบบ, project status, Master Skills/สกิลที่เกี่ยวข้อง, API และรายงานใน changeset เดียวกัน หากบางรายการไม่กระทบให้ระบุเหตุผล

## ตัวอย่างการอธิบายที่ครบ

“งานแล็บสอบเทียบใช้มาตรวิทยา คุณภาพ สถิติ และเอกสารสอบกลับ คนที่แม่นตัวเลขและละเอียดช่วยเรียน/ตรวจวัดดีขึ้น แต่ต้องมีการฝึก ลงมือใช้เครื่องมือ และเครื่องอ้างอิงพร้อม ทีมอาจแบ่งผู้วิเคราะห์กับผู้จัดเอกสารได้ หากขาดผู้เชี่ยวชาญหลักต้องหยุดรับงานใหม่ ผู้เล่นดูเหตุผลและผู้รู้ในหน้าบริษัทได้”
