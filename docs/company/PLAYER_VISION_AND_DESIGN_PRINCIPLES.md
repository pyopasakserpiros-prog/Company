# ความต้องการของผู้เล่นและหลักออกแบบเกม

บันทึกจากคำชี้แจงผู้ใช้วันที่ 11 พฤศจิกายน 2026 เอกสารนี้บอกทิศทางและข้อเสนอเพื่อพัฒนา ไม่ได้ยืนยันว่าฟีเจอร์ด้านล่างมีแล้ว และไม่อนุญาตให้แก้ AGENTS.md หรือกฎเหล็ก

## ผู้ใช้ต้องการประสบการณ์แบบไหน

ผู้ใช้ไม่มีความรู้ด้านการเขียนโค้ด ชอบเล่นเกม แต่ไม่จำเป็นต้องรู้ว่าจะพัฒนาอย่างไรหรือระบุฟีเจอร์ที่อยากได้ครบตั้งแต่ต้น ทีมต้องช่วยคิด วิเคราะห์ เสนอไอเดีย และออกแบบเพิ่มเติม ไม่รอให้ผู้ใช้คิดทุกอย่างหรือทำเพียงรายการตามตัวอักษร

ความสนุกหลักคือการเฝ้าดูโลกที่ NPC ใช้ชีวิตและตัดสินใจเองตามนิสัย สภาพชีวิต ความสามารถ ความสัมพันธ์ ข้อมูล และทรัพยากรที่มี ผู้ใช้ชอบสังเกตว่าเกิดอะไรขึ้น ทำไมจึงเกิด และเมื่อเปลี่ยนเงื่อนไขแล้วโลกเปลี่ยนไปอย่างไร

สิ่งที่ผู้ใช้ชอบทดลอง:
- เปลี่ยนนิสัยของ NPC แล้วดูพฤติกรรม ความสัมพันธ์ และการตัดสินใจที่เปลี่ยนตาม
- แก้เงื่อนไขของบริษัท เพิ่มเงิน หรือเสกสิ่งของ แล้วดูว่าบริษัท/ผู้บริหาร/พนักงานนำทรัพยากรไปใช้อย่างไร
- ดูเหตุการณ์ที่เกิดจากการดำเนินชีวิตและผลสะสมของการตัดสินใจ โดยไม่ต้องกดสั่งบริหารงานประจำแทน NPC

## หน้าที่ร่วมของ Codex, Agy และแอปแชต

ทุกฝั่งต้องช่วยคิดไอเดียเอง เสนอสิ่งที่ผู้ใช้อาจยังนึกไม่ถึง และใช้วิจารณญาณภายในงานที่ได้รับอำนาจ อธิบายด้วยภาษาผู้เล่น เหตุการณ์ตัวอย่าง และผลต่อความสนุก ไม่โยนการเลือกระบบทางเทคนิคหรือการออกแบบทั้งหมดให้ผู้ใช้

เมื่อเป้าหมายไม่ครบ ให้ใช้บริบทเกมเสนอทางที่เหมาะพร้อมเหตุผล ถามเฉพาะสิ่งที่เปลี่ยนประสบการณ์หรือขอบเขตอย่างมีนัยสำคัญ ตัดสินใจรายละเอียดตามปกติได้โดยเคารพสิทธิ/ข้อจำกัดที่ได้รับ

เก็บไอเดียใหม่ใน ideas หรือเอกสารเสนอที่ค้นพบใน repo ได้ แยกสิ่งที่คิดไว้กับสิ่งที่ทำแล้ว เมื่อผู้ใช้มอบหมายพัฒนาให้ทำงานให้ครบขอบเขต ส่วนงานเดียวที่ Gemini กำลังทำอยู่ให้ประสานตาม workflow เพื่อไม่แก้ทับกัน

AGENTS.md คือกฎเหล็ก ห้ามแก้โดยไม่ได้รับอนุญาตจากผู้ใช้โดยตรง ข้อเสนอใหม่หรือสิทธิให้สร้างสรรค์ไม่ได้อนุญาตให้เปลี่ยนไฟล์กฎนี้ ออกข้อเสนอแยกและชี้จุดที่ขัดกฎเมื่อจำเป็น

## หลักการของโลก NPC

1. บุคลิกส่งผลต่อการชั่งน้ำหนักทางเลือกจริงร่วมกับสถานการณ์ ไม่ใช่แค่เปลี่ยนข้อความความคิด และไม่บังคับผลแบบ "คนชอบเสี่ยงต้องลงทุนทุกครั้ง"
2. NPC มีชีวิตและความต้องการนอกการผลิต การพัก ความสัมพันธ์ การเรียนรู้ และชีวิตส่วนตัวควรเชื่อมผลต่อกันตามระบบที่พัฒนาจริง
3. ทรัพยากรเพิ่มเปิดทางเลือก แต่เงินไม่แทนความรู้ เทคโนโลยี ทีม เครื่องจักร ตลาด หรือภาระหนี้ NPC อาจเก็บเงิน ลงทุน ฝึกคน หรือปฏิเสธโอกาสด้วยเหตุผล
4. ความเป็นธรรมชาติมาจากเหตุและผลของสถานะจำลอง ไม่อ้างว่าเป็นการตัดสินใจจริงถ้ามีเพียงข้อความสุ่มหรือสคริปต์ที่บังคับผลลัพธ์เดียวทุกคน
5. ผู้เล่นควรมองเห็นการตัดสินใจและผลตามมา เช่น เหตุการณ์ ผู้ที่เกี่ยวข้อง ความเปลี่ยนแปลงก่อน/หลัง และคำอธิบายสั้นที่อิงข้อมูลจริง
6. การแก้ข้อมูลเฉพาะ NPC เป็นการทดลองที่ผู้ใช้ต้องการ ต้องผ่าน API/validation และไม่แก้สูตร Human Core ที่ล็อกหรือทำให้ NPC อื่นถูกแก้ตามโดยไม่ตั้งใจ
7. การเพิ่มเงิน/เสกของผ่าน Edit Hub เป็นการทดลองที่ได้รับอนุญาต ต้องบันทึกแหล่งที่มาว่าเป็นการแก้จากผู้เล่น แยกจากรายได้ดำเนินงาน ส่วนการทำงานปกติของ NPC ยังต้องอนุรักษ์เงินและทรัพยากรตามกฎ

## Edit Hub ต้องใช้ง่ายสำหรับผู้เล่นที่ไม่รู้โค้ด

ข้อกำหนดจากผู้ใช้: Edit Hub ต้องเข้าใจและใช้งานได้ง่าย ไม่ต้องรู้ศัพท์เขียนโปรแกรม จำรหัสวัตถุดิบ หรือแก้ JSON เอง

แนวออกแบบต่อไปนี้เป็นข้อเสนอให้ผู้พัฒนาเลือก/ปรับ ต้องตรวจ UI จริงก่อนเริ่มและไม่กล่าวว่าได้ทำแล้ว:

- เลือกเป้าหมายให้ชัดก่อน: NPC คนไหนหรือบริษัทไหน ใช้ชื่อ ภาพ และข้อมูลพอแยกได้ ไม่พึ่ง ID ภายใน
- ใช้ภาษาไทยอ่านง่าย จัดหมวดนิสัย/ค่านิยม/ความถนัด/สถานะและค้นหาได้ ไม่วางค่าทั้งหมดรวมเป็นรายการยาวโดยไม่มีคำอธิบาย
- แสดงคำอธิบายสั้นของค่า ใช้ตัวเลื่อนพร้อมตัวเลขหรือวิธีปรับที่เหมาะกับมือถือ และมีค่าปัจจุบันให้เทียบ ปุ่ม/ช่องกรอกต้องแตะง่าย ตัวเลขไม่ล้นจอ
- แสดงผลที่อาจเกิดเป็นแนวโน้ม เช่น "อาจให้น้ำหนักความมั่นคงมากขึ้น" ไม่รับประกันว่าจะทำงานใดแน่นอน เพราะสถานการณ์และเงื่อนไขอื่นยังมีผล
- เพิ่มเงินด้วยหน่วยบาทที่ผู้เล่นเข้าใจ การแปลงเป็นสตางค์/ตรวจช่วงค่าเป็นหน้าที่ระบบ มีรายละเอียดว่าบริษัทหรือกระเป๋า NPC ใครได้รับ ไม่ปะปนสองบัญชี
- เสกของจากรายการชื่อ/ภาพ มีค้นหา หมวด จำนวน หน่วย และของที่มีอยู่ ไม่ให้ผู้เล่นพิมพ์ materialId เอง
- ตรวจค่าที่กรอกและแจ้งวิธีแก้ด้วยข้อความธรรมดา คงค่าที่ผู้เล่นกำลังกรอกเมื่อยังไม่ผ่าน และไม่ใช้ข้อความ error ภายในเป็นคำอธิบายหลัก
- ก่อนนำค่าไปใช้ให้เห็นรายการเปลี่ยนแปลงและเป้าหมายชัดเจน เลี่ยงหน้าต่างยืนยันหลายชั้นในงานทั่วไป มีทางยกเลิกค่าที่ยังไม่ใช้ หากเสนอ undo ต้องแยกคืนค่าเดิมจากการย้อนผลจำลองที่เกิดไปแล้ว และไม่สัญญาย้อนเวลาถ้ายังไม่มีระบบรองรับ
- หลังแก้ บอกว่าค่าใดถูกนำไปใช้แล้ว และให้ติดตาม NPC/บริษัทเดิมต่อได้สะดวก อาจมีบันทึกก่อน/หลัง เหตุการณ์ที่เกี่ยวข้อง หรือทางบันทึก/โหลดสถานการณ์ทดลอง หากฐานจริงรองรับ
- ปิด Edit Hub และกลับไปดูโลกได้ง่ายบนมือถือและเดสก์ท็อป เมนูไม่บดบังเหตุการณ์จนการทดลองใช้งานลำบาก

การเพิ่มเงิน/เปลี่ยนเงื่อนไขบริษัทไม่ได้แปลว่าต้องเพิ่มปุ่มบังคับ CEO เปิดธุรกิจหรือกดสั่งงานประจำให้ผู้เล่น ผู้เล่นปรับสภาพตั้งต้นและสังเกตว่า NPC เลือกทำอะไรเอง

## ตัวอย่างคำถามที่ทีมควรช่วยออกแบบให้ผู้เล่นสำรวจได้

- CEO คนเดิมแต่มีเงินสำรองมากขึ้นจะลงทุน ฝึกทีม ชำระหนี้ หรือยังเลือกเก็บเงิน เพราะอะไร?
- พนักงานที่ถูกปรับนิสัยจะเลือกพัก เรียนรู้ เข้าหาคนอื่น หรือรับงานต่างจากเดิมอย่างไรภายใต้สภาพเดียวกัน?
- เมื่อเพิ่มวัตถุดิบแล้วคอขวดหายไป บริษัทเปลี่ยนการผลิต/รับงานหรือยังติดเครื่องจักร ความรู้ และคน?

นี่คือโจทย์และทิศทางการออกแบบ ไม่ใช่ผลทดสอบหรือการรับประกันพฤติกรรมปัจจุบัน ผู้พัฒนาต้องตรวจและแสดงหลักฐานจากการทำงานจริงเมื่อทำระบบเหล่านี้
