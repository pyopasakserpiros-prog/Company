# เอกสาร สกิล รายงาน และการตรวจสิ่งส่งมอบ

ใช้กับทุกงานที่แก้ไขหรือส่งมอบโครงการ ทั้ง Codex, Agy และแอปแชต อ่าน AGENTS.md ก่อนเริ่มทุกครั้ง เอกสารนี้อธิบายวิธีปฏิบัติ ไม่ให้สิทธิแก้ AGENTS.md โดยอัตโนมัติ

## งานยังไม่จบจนเอกสารและหลักฐานตรงกับสิ่งที่ส่ง

ทุกครั้งที่มีงานแก้ไข/ส่งมอบ ต้องอัปเดต project status เขียนรายงานงาน และทบทวนสกิลกับเอกสารที่ได้รับผลกระทบ เอเจนต์เป็นผู้ค้นหาและเลือกไฟล์เอง ไม่รอให้ผู้ใช้บอกชื่อเอกสารทั้งหมด งานเอกสารล้วนให้ระบุว่าเปลี่ยนกระบวนการ/เอกสารและไม่มีฟีเจอร์เกมใหม่ ไม่เพิ่มเลขรุ่นเกมหรืออ้างผลทดสอบใหม่โดยไม่มีเหตุ

รายงานสิ่งที่ตรวจแล้วแต่ไม่ต้องแก้ด้วยเหตุผลได้ ไม่ต้องแก้ทุกเอกสารที่ไม่เกี่ยวข้องเพื่อให้ดูครบ แต่ห้ามข้ามสกิลที่วิธีทำงาน/สัญญาระบบเปลี่ยน และห้ามใช้แค่แก้วันที่แทนการปรับเนื้อหาที่ผิด

## แผนที่เอกสารและผู้ดูแล

ผู้ทำงานนั้นเป็นผู้รับผิดชอบให้เอกสารครบ ผู้รับช่วงตรวจทานอีกครั้งก่อนรวมเข้าระบบ ใช้ตารางนี้เป็นขั้นต่ำและค้นหา references/สำเนาอื่นเพิ่มเอง

| งาน/ผลกระทบ | เอกสารที่ต้องทบทวนและอัปเดต |
|---|---|
| ทุกงานแก้ไขและส่งมอบ | project_status_and_ai_onboarding.md และสำเนาใน COMPANY_SOURCE, รายงานงาน, AGENT_WORK_STATUS เมื่อสถานะงานร่วมเปลี่ยน, สกิลที่เกี่ยวข้อง |
| ขั้นตอนพัฒนา/ตรวจ/แพ็ก/รับช่วง | company-for-every-patch ทั้งสองสำเนา, workflow, README/START_HERE, เอกสารส่งต่อ/พรอมต์ที่เกี่ยวข้อง |
| ความสามารถ/โครงสร้างเกม/สัญญาใหม่ | company-evolution-dev ทั้งสามสำเนา, project status, รายงาน, คำอธิบาย API/ระบบที่เปลี่ยน |
| API, snapshot, commands, save | docs/company/design/PRESENTATION_API.md, schema/คำสั่งที่เกี่ยวข้อง, วิธีใช้/ข้อจำกัดเซฟ และเทสต์ตามผลกระทบ |
| NPC/ชีวิต/การตัดสินใจ/Edit Hub/UI | วิสัยทัศน์ผู้เล่น, คู่มือ UI/API ที่ได้รับผลกระทบ, ข้อเสนอที่เกี่ยวข้อง และภาพ/หลักฐานตามที่ตรวจจริง |
| สินค้า วัตถุดิบ เทคโนโลยี ธุรกิจ | แผน/สเปก supply chain, coverage, ideas ที่เกี่ยวข้อง และสกิล master; snapshot แค็ตตาล็อกที่มีชื่อรุ่นเก่าให้คงเป็นหลักฐานฐานเดิม ไม่เขียนทับให้กลายเป็นรุ่นใหม่โดยเงียบ ๆ |
| วิธีเปิด/ติดตั้ง/build/เทสต์ | README ราก, COMPANY_SOURCE/README.md, START_HERE, package manifest/lock เมื่อจำเป็น และสกิล workflow |
| ไอเดียที่ทำเสร็จจริง | นำเฉพาะส่วนที่ยืนยันแล้วออกจาก ideas ไปสรุปใน project status พร้อมลิงก์รายงาน เก็บส่วนที่ยังไม่ทำ/ทำบางส่วน และแก้ดัชนี/ลิงก์ |
| เพิ่มไฟล์ใหม่ ย้าย หรือลบไฟล์ | ดัชนีรายงาน/เอกสาร ลิงก์ข้ามไฟล์ รายการเปลี่ยนแปลงในรายงาน/manifest และจุดอ่านรับช่วง |

## ไฟล์หลักและสำเนาที่ต้องตรงกัน

- สถานะโครงการหลัก: `project_status_and_ai_onboarding.md`; สำเนาใช้งาน: `COMPANY_SOURCE/project_status_and_ai_onboarding.md` ให้เนื้อหาตรงกันหลังแก้
- Master skill หลัก: `.agents/skills/company-evolution-dev/SKILL.md`; สำเนา: `SKILL.md` และ `SKILL_COMPANY_EVOLUTION_DEV.md` ให้ตรงกัน
- Workflow skill หลัก: `.agents/skills/company-for-every-patch/SKILL.md`; สำเนา: `SKILL_COMPANY_FOR_EVERY_PATCH.md` ให้ตรงกัน
- รายงานใหม่เก็บใน `docs/company/PATCH_REPORTS/` และปรับดัชนี สำเนา `PATCH_REPORTS/` ที่โครงการใช้อยู่ต้องตรงกัน ไฟล์รายงานเก่าไม่ถูกเขียนทับด้วยผลครั้งใหม่
- ทะเบียนงาน `docs/company/AGENT_WORK_STATUS.md` บอกว่าใครทำอะไร ไม่ใช้แทน project status ที่บอกว่าเกมทำอะไรได้
- `START_HERE_FOR_AI.md` เป็นจุดนำทางไปข้อมูลปัจจุบัน ไม่ทำให้รายงานประวัติกลายเป็นคำสั่งหรือผลตรวจล่าสุด

ตรวจตำแหน่งจริงก่อนใช้และเพิ่มรายการสำเนาในตารางนี้เมื่อโครงสร้างเปลี่ยน ถ้าในแอปมีเครื่องมืออัปเดต installed skill ให้ซิงก์หลังแก้ไฟล์ด้วย ถ้าไม่มี ให้ส่งไฟล์ SKILL.md ที่อัปเดตใน ZIP พร้อมระบุว่าสกิลในแอปยังไม่ได้ซิงก์ ห้ามอ้างว่าเรียก skills:update_skill สำเร็จถ้าไม่มีเครื่องมือนั้น

## รายงานการอัปเดตที่ต้องมีทุกงาน

งานพัฒนาเกมใช้ชื่อรุ่น/งานที่สื่อขอบเขต ส่วนงานเอกสาร/เครื่องมือใช้วันที่และ task ID โดยไม่ต้องปลอมว่าออกรุ่นเกมใหม่ รายงานต้องมี:

1. เป้าหมาย ผู้ทำงาน วันที่ ขอบเขต/ฐาน source และฐานเอกสารหรือ commit ที่ได้รับ
2. ปัญหาหรือความต้องการเดิม สิ่งที่แก้ และผลที่เกิดจริง รวมเหตุผลการออกแบบและไอเดียที่ผู้พัฒนาคิดต่อเอง
3. ไฟล์เพิ่ม/แก้/ลบ เอกสาร/สกิล/สำเนาที่ซิงก์ และไฟล์ที่ทบทวนแล้วไม่เปลี่ยนพร้อมเหตุผล
4. สิ่งที่เสร็จ บางส่วน เลื่อน และข้อจำกัด แยกสิ่งที่เสนอจากสิ่งที่ใช้งานแล้ว
5. คำสั่งที่รันจริง สภาพแวดล้อมเท่าที่มีผล ผล/จำนวน/เวลาที่อ่านได้ และหลักฐาน ห้ามคัดผลหรือจำนวนเทสต์รุ่นก่อนมาอ้างเป็นครั้งใหม่
6. วิธีเปิด/ตรวจซ้ำ ความเสี่ยงที่ยังมี งานถัดไป และการรับช่วงที่จำเป็น
7. สถานะสิ่งส่งมอบ: repo commit/branch หรือ ZIP พร้อมชื่อ/ฐาน/ผลตรวจ ZIP ระบุว่าไม่ใช้กับงานนี้ได้เมื่อไม่ได้ส่งเป็น ZIP

ตรวจเอกสารล้วนตามลิงก์ ความครบถ้วน ความสอดคล้องและขอบเขตไฟล์ งาน source ตรวจตาม AGENTS/README และผลกระทบ การระบุว่าไม่รันเทสต์เกมเพราะเป็นงานเอกสารต้องชัด ไม่รายงานว่าเทสต์เกมผ่านจากการตรวจ Markdown

## ZIP โครงการฉบับส่งกลับต้องรวมสิ่งที่พัฒนาต่อได้ทั้งหมด

สำหรับเอเจนต์แอปแชต ให้ส่ง ZIP โครงการที่อัปเดตครบ ไม่ใช่เฉพาะโค้ดที่แก้ ไม่ใช่เพียง HTML หรือรายงาน เว้นแต่ผู้ใช้ขอ ZIP เอกสาร/แพตช์ย่อยอย่างชัดเจนและระบุประเภทบนชื่อไฟล์/README

สิ่งที่ต้องอยู่ใน ZIP เกมเต็มตามโครงสร้างโครงการจริง:
- source, HTML ต้นทาง, CSS, assets และไฟล์ที่เกมใช้อ้างอิง รวม license/เครดิตที่ต้องส่งพร้อมงาน
- package.json/lockfile, เครื่องมือ build/ตรวจ/เทสต์ และ fixtures ที่จำเป็นต่อการเปิดพัฒนาต่อ
- ไฟล์เกมเดี่ยวที่ build จาก source ปัจจุบัน และ alias ที่โครงการยังแจก/ใช้งาน ต้องตรงกับผล build เดียวกัน อย่าแก้ HTML ที่ build แล้วแยกจาก source
- AGENTS.md ฉบับที่ได้รับหรือฉบับที่ผู้ใช้อนุญาตให้แก้, README, START_HERE, project status ทุกสำเนา, SKILL.md ที่เกี่ยวข้องและ **โฟลเดอร์ซ่อน .agents/skills** ห้ามตกเพราะใช้ glob ที่ไม่รวมไฟล์ซ่อน
- เอกสาร API/สเปก/ideas/ดัชนี/พรอมต์/ทะเบียนงานของโครงการที่ยังจำเป็น รายงานอัปเดตและผลตรวจครั้งนี้ รวมไฟล์เดิมที่ไม่ได้แก้และยังเป็นส่วนของโครงการ
- `HANDOFF_MANIFEST.json` และ `ZIP_VALIDATION_REPORT.md` ตามขั้นตอนตรวจด้านล่าง

ไม่รวม .git, node_modules, cache, ZIP ซ้อน/ZIP ต้นทาง, credentials/ไฟล์ .env ส่วนตัว, เซฟจริงของผู้ใช้, เกมอื่นหรือ artifacts ไม่เกี่ยวข้อง คงตัวอย่างตั้งค่า/fixture ที่ไม่เป็นความลับและจำเป็นไว้ อย่าตีความว่า "รวมทุกอย่าง" ต้องใส่ dependencies ที่ติดตั้งหรือข้อมูลส่วนตัว

## ตรวจจาก ZIP สุดท้ายก่อนส่ง ไม่ตรวจเฉพาะโฟลเดอร์ต้นทาง

1. เตรียม staging นอกโฟลเดอร์ที่จะถูกแพ็ก ล็อกรายการไฟล์หลัง source/build/เอกสาร/สกิล/รายงานครบ เพื่อไม่รวม ZIP ของตัวเองหรือไฟล์ชั่วคราว
2. สร้าง `HANDOFF_MANIFEST.json`: task ID, ชนิดแพ็ก, base source commit/รุ่น, ผู้ทำงาน, เอกสารฐาน, เพิ่ม/แก้/ลบ, รายการยกเว้นและเหตุผล, path/size/SHA-256 ของทุกไฟล์ payload ไม่รวม manifest ตัวเอง การไม่มีไฟล์ใน ZIP ไม่ถือเป็นคำสั่งลบจาก repo โดยอัตโนมัติ
3. สร้าง ZIP แล้วเปิดอ่านจริง ตรวจ ZIP integrity/CRC, รายการและจำนวนไฟล์, ขนาด, โครงสร้าง root ที่ประกาศ, ไฟล์จำเป็นและ .agents/skills ตรวจไม่มี path absolute/.., ชื่อซ้ำ, nested ZIP หรือรายการยกเว้นที่หลุดมา
4. แตก ZIP ในโฟลเดอร์ว่างใหม่โดยไม่พึ่ง source ต้นทาง เทียบรายการ/size/hash กับ manifest และค้นหาไฟล์ที่อ้างอิงหายหรือลิงก์ไป path ของเครื่องผู้พัฒนา
5. สำหรับ ZIP เกมเต็ม ตรวจ core/ไวยากรณ์ และรันขั้นตอน build/เทสต์ที่กำหนดจากสำเนาที่แตกใหม่ตามสภาพแวดล้อม ติดตั้งผ่าน manifest/lockfile เมื่อจำเป็น ไม่ยัด node_modules ลง ZIP เพื่อแก้ปัญหา ถ้าส่งไฟล์เล่นเดี่ยว ให้เทียบกับ build ใหม่จาก source ใน ZIP และเปิดเกมตรวจเบื้องต้น/เบราว์เซอร์ตามขอบเขต
6. บันทึกสิ่งที่ตรวจจริงใน `ZIP_VALIDATION_REPORT.md`: ชื่อแพ็ก ฐาน จำนวนไฟล์ เงื่อนไขตรวจ ผล CRC/manifest/ไฟล์จำเป็น/ลิงก์/สกิล/สถานะ/core/build/เทสต์ และสิ่งที่ตรวจไม่ได้พร้อมเหตุผล นำรายงานเข้าชุด ปรับ manifest และแพ็กใหม่ถ้าต้องเพิ่ม/แก้ไฟล์ จากนั้น **ตรวจ ZIP สุดท้ายซ้ำ** ให้แน่ใจว่าไม่ได้ส่งคนละชุดกับที่ตรวจ หาก payload เปลี่ยนให้ตรวจส่วนที่ได้รับผลอีกครั้ง
7. คำนวณ SHA-256 ของ ZIP สุดท้ายและแจ้งพร้อมลิงก์ดาวน์โหลด/ไฟล์ checksum ภายนอกได้ ไม่ฝัง hash ของ ZIP เองใน ZIP จนเกิดการอ้างตัวเอง รายงานภายในเก็บผลตรวจ payload/วิธีตรวจ ส่วนค่า hash ของ artifact สุดท้ายอยู่ภายนอก
8. ส่งไฟล์ที่ตรวจแล้วและบอกผลสั้น ๆ ไม่อ้างว่า ZIP พร้อมเล่น/ตรวจครบถ้ามีคำสั่งสำคัญที่ยังรันไม่ได้ ต้องระบุสถานะ unverified/ข้อจำกัดตามจริงและเก็บงานที่ทำไว้สำหรับตรวจต่อ

ไม่ต้องสร้าง ZIP ในทุกงานที่ส่งตรงผ่าน repo แต่กติกาทั้งหมดนี้บังคับเมื่อสิ่งส่งมอบเป็น ZIP เกม/เอกสารตามขอบเขตนั้น ZIP เอกสารตรวจความครบ/ลิงก์/manifest ตามเนื้อหา ไม่อ้างว่าทดสอบการเล่นเกมแล้ว

## ก่อนจบงาน

ทบทวน git diff/รายการไฟล์และ remote ล่าสุด ตรวจว่า source กับไฟล์เล่นตรงกันเมื่อมีการเปลี่ยนเกม รายงานกับ project status สอดคล้องกัน สำเนาสกิล/สถานะ/รายงานตรงกัน ลิงก์ดัชนีใช้ได้ และสิ่งส่งมอบตรงกับที่ตรวจ สรุปผู้ใช้ด้วยภาษาง่าย: ทำอะไร ผลเป็นอย่างไร อยู่ที่ไหน และยังค้างอะไร
