# Workflow ร่วมพัฒนาเกม Company

## ทีมและช่องทางทำงาน

การพัฒนามี 3 ฝั่งหลัก ผู้ใช้เป็นผู้กำหนดเป้าหมายและส่งไฟล์ระหว่างฝั่ง:

| ฝั่ง | เข้าถึง GitHub/repo โดยตรง | งานที่ทำได้และการส่งต่อ |
|---|---|---|
| Codex | ได้ | อ่าน/แก้ repo พัฒนา ตรวจแพตช์ รวมงาน อัปเดตเอกสาร และ commit/push ตามงานที่ได้รับ |
| Agy | ได้ | อ่าน/แก้ repo พัฒนา ตรวจแพตช์ รวมงาน อัปเดตเอกสาร และ commit/push ตามงานที่ได้รับ เช่นเดียวกับ Codex |
| แอปแชต Gemini หรือ ChatGPT | ไม่ได้ ใน workflow นี้ | รับ ZIP และพรอมต์จากผู้ใช้ พัฒนาในสภาพแวดล้อมของแอป แล้วส่ง ZIP ที่อัปเดตกลับให้ผู้ใช้ ห้ามอ้างว่าอ่าน repo สดหรือ push GitHub แล้ว |

Gemini กับ ChatGPT แบบแชตเป็นผู้ช่วยในช่องทางส่งต่อเดียวกัน ไม่จำเป็นต้องทำงานแพตช์เดียวพร้อมกัน บทบาทขึ้นกับสิ่งที่ผู้ใช้มอบหมาย ไม่ถือว่า Codex ต้องเป็นผู้พัฒนาหรือผู้รวมงานทุกครั้ง

อ่าน AGENTS.md, START_HERE_FOR_AI.md และสถานะโครงการก่อนลงมือ ใช้กฎเหล็กเรื่อง Human Core, NPC อัตโนมัติ, บัญชี, simulation/API และไฟล์เกมตามเดิม คำสั่งล่าสุดของผู้ใช้มีลำดับเหนือ workflow นี้

## ความรับผิดชอบต่อผู้เล่นและกฎเหล็ก

ผู้ใช้ไม่มีพื้นฐานเขียนโค้ดและอาจยังอธิบายฟีเจอร์ที่อยากได้ไม่ครบ ทุกฝั่งต้องช่วยคิด เสนอ และออกแบบต่อยอดภายใต้ขอบเขตงาน โดยอ่าน [วิสัยทัศน์ผู้เล่นและหลัก Edit Hub](PLAYER_VISION_AND_DESIGN_PRINCIPLES.md) เป้าหมายคือโลก NPC ที่ใช้ชีวิตเองตามนิสัยและเหตุผลของสถานการณ์ ผู้เล่นแก้เงื่อนไขแล้วเฝ้าดูผลได้ง่าย

**AGENTS.md คือกฎเหล็ก ห้ามแก้ไฟล์นี้โดยไม่ได้รับอนุญาตจากผู้ใช้โดยตรง** อำนาจสร้างสรรค์หรือคำขอแก้โค้ด/เอกสารทั่วไปไม่ใช่สิทธิเปลี่ยนกฎ เสนอแนวคิดที่อาจขัดกฎในเอกสารแยกและระบุความขัดแย้งก่อนดำเนินส่วนที่ต้องเปลี่ยนกฎ

ถ้าคำชี้แจงใหม่ถูกเพิ่มใน repo ขณะที่แอปแชตทำงานจาก ZIP เก่า ให้บันทึกว่าเป็นข้อมูลเสริมที่ยังไม่ได้ยืนยันการส่งถึงแอป อย่าอ้างว่า Gemini/ChatGPT ได้อ่านการอัปเดต GitHub แล้ว ผู้ใช้เป็นช่องทางส่งข้อความ/ไฟล์เสริม

## ก่อนเริ่มหรือเปลี่ยนงาน

1. Codex/Agy ตรวจ branch, commit, remote และไฟล์ค้าง พร้อมอ่าน [สถานะงานเอเจนต์](AGENT_WORK_STATUS.md) และพรอมต์ของงานที่กำลังทำ
2. ลงทะเบียนงานด้วยชื่อสั้น ผู้รับผิดชอบ ขอบเขต/ไฟล์ที่คาดว่าจะกระทบ base commit สถานะ และผู้รับช่วงต่อ ถ้ายังไม่ทราบว่าใครรวมงาน ให้ระบุว่ายังไม่กำหนดแทนการมอบหมายให้คนอื่นเอง
3. ระบุผู้รับผิดชอบหลักหนึ่งฝั่งต่อขอบเขตเดียวกัน งานต่างส่วนทำคู่ขนานได้ แต่หลีกเลี่ยงแก้ simulation/catalog/ไฟล์ build ก้อนเดียวกันโดยไม่ประสานไว้ในเอกสาร ถ้าจำเป็นต้องแตะร่วม ให้แบ่งงาน/ไฟล์หรือรอรับช่วง
4. อย่าทิ้ง/reset/เขียนทับงานอีกฝั่งหรือ force push เพื่อทำให้ฐานตรงกัน ถ้า checkout สกปรกให้รักษางานและใช้ branch/worktree แยกตามเหมาะสม
5. หลังเปลี่ยนขอบเขต ฐาน หรือสถานะ ให้ปรับบันทึกทันที และระบุ dependency/blocker ตามจริง เอเจนต์ใน repo ต้องอ่านบันทึกนี้ ไม่อาศัยประวัติแชตที่อีกฝั่งอาจมองไม่เห็น

## A. ส่งงานจาก repo ไปให้แอปแชต

1. ผู้เตรียมงาน Codex หรือ Agy ระบุว่าใช้ source base commit ไหน รุ่นเกมไหน และพรอมต์ revision/commit ไหน ถ้ามีเฉพาะข้อเสนอและผู้ใช้บอกว่าแอปมี ZIP เกมแล้ว ให้ระบุฐาน ZIP ที่แอปมี ไม่เรียก ZIP ข้อเสนอว่า ZIP เกมเต็ม
2. เขียนพรอมต์ที่มีเป้าหมาย ขอบเขต กฎเหล็ก ข้อมูลที่พบจริง แนวเสนอ เกณฑ์ตรวจรับ และสิ่งส่งมอบ ใส่ไว้ใน docs/company และเชื่อม ideas ที่เกี่ยวข้องให้ค้นพบใน repo
3. แพ็ก source ที่พัฒนาได้จริงพร้อมเอกสาร/เครื่องมือ/เทสต์ที่อยู่ในโครงการ และไฟล์เล่นเดี่ยวที่ build แล้วเมื่อเป็น ZIP เกมเต็ม หากเป็น ZIP เอกสารอย่างเดียวให้ตั้งชื่อและ README ให้ชัดว่าไม่มีเกม
4. แนบข้อมูลฐาน/รายการไฟล์ที่ต้องสนใจ/สิ่งที่ยังไม่ได้ทำ แนะนำให้มี manifest บอก base commit, เวอร์ชัน, task ID, scope และรายการเปลี่ยนแปลง; checksum ช่วยยืนยันฐานได้
5. ตรวจ ZIP ว่าเปิดได้ โครงสร้างไม่ซ้อนผิดชั้น ไม่มี .git, node_modules, cache, ZIP ซ้อน เกม JS2 หรือข้อมูลส่วนตัวที่ไม่เกี่ยวข้อง ห้ามตัดไฟล์ source/test ที่ต้องใช้เพื่อทำงานออกจนเหลือแค่ HTML
6. ส่งลิงก์ดาวน์โหลดและพรอมต์ให้ผู้ใช้ ผู้ใช้เป็นคนส่งให้แอป ไม่มีการอ้างว่าได้ส่งข้อความหา Gemini/ChatGPT โดยตรง บันทึก sent เมื่อผู้ใช้ได้รับแพ็ก และ in_progress เมื่อผู้ใช้แจ้งว่าแอปเริ่มทำแล้ว

## B. การทำงานของ Gemini/ChatGPT ในแอปแชต

- อ่านกฎและโค้ดใน ZIP จริง เอกสารเป็นข้อมูลประกอบ หากเอกสารเก่าขัดกันให้เทียบ source และคำสั่งล่าสุด ไม่สมมติว่าตนเห็นการแก้ GitHub หลังวันที่สร้าง ZIP
- ให้ Gemini คิดเอง วิเคราะห์เอง สร้างไอเดียใหม่ และใช้วิจารณญาณออกแบบเพิ่มเติมด้วย พรอมต์และ ideas เป็นข้อเสนอเพื่อใช้ต่อยอด ไม่จำกัดความคิดไว้ที่รายการนั้น
- Gemini เลือกปรับ รวม ตัด หรือเพิ่มแนวคิด แก้ปัญหาเฉพาะหน้า และกำหนดรายละเอียดได้ภายในงานที่ผู้ใช้มอบหมาย โดยไม่ขัดกฎเหล็ก อธิบายการตัดสินใจสำคัญและ tradeoff ในรายงาน ไม่ต้องถามผู้ใช้ทุกตัวเลขหรือทุกรายละเอียด
- ความสร้างสรรค์ไม่ใช่เหตุให้แก้ Human Core ที่ล็อก เปลี่ยนเกมเป็นให้ผู้เล่นบริหารเอง สร้างทรัพยากร/เทคโนโลยีฟรี หรืออ้างผลตรวจที่ไม่ได้รัน ถ้าทำไม่ครบให้บอก completed/partial/deferred ตามจริง
- อัปเดต source ก่อน build ไฟล์ HTML ตรวจผลตามขั้นตอนของแพตช์ ไม่แก้แต่ไฟล์ build จน source กับเกมที่ส่งไม่ตรงกัน

## C. สิ่งที่แอปต้องส่งกลับเป็น ZIP

ส่ง ZIP โครงการที่อัปเดตและเปิดพัฒนาต่อได้ ไม่ส่งเพียงข้อความ อธิบายโค้ด หรือ HTML เดี่ยว เว้นแต่ผู้ใช้ระบุสิ่งส่งมอบอย่างอื่นโดยตรง

ZIP เกมเต็มควรมี source ปัจจุบัน เครื่องมือ build/ตรวจ เทสต์และ dependencies manifest ที่โครงการต้องใช้ เอกสารกฎ/สถานะ ไฟล์เล่นเดี่ยวที่ build จาก source และรายงานแพตช์

รายงานระบุฐานที่ได้รับ รุ่นใหม่ รายการไฟล์เพิ่ม/แก้/ลบ ฟีเจอร์ที่เสร็จ/บางส่วน/เลื่อน เหตุผลการเลือกออกแบบ วิธีเปิดเกม คำสั่งตรวจ ผลที่รันจริงและข้อจำกัด รวมถึงสิ่งที่คิดใหม่หรือปรับจากข้อเสนอ ถ้าไฟล์ควรถูกลบต้องบอกชัด ไม่ถือว่าการไม่แนบไฟล์นั้นเท่ากับอนุมัติลบไฟล์ใน repo

คงกติกาแพ็ก ZIP เดิม: ไม่ใส่ .git, node_modules, cache, ZIP ซ้อน หรือเกมอื่นที่ไม่เกี่ยวข้อง ใช้เครื่องมือไฟล์ที่มีจริงในแอปเพื่อแนบ ZIP ให้ผู้ใช้ดาวน์โหลดได้ ถ้าไม่มีเครื่องมือ google:show_file หรือ path รุ่นเก่าที่เอกสารเคยกล่าวถึง ให้ใช้ทางแนบไฟล์ที่มีจริง ห้ามอ้างว่าเรียกเครื่องมือสำเร็จทั้งที่ไม่มี

## D. รับ ZIP กลับมาตรวจและรวมเข้า repo

1. ผู้ใช้ส่ง ZIP กลับให้ Codex หรือ Agy ผู้รับช่วงลงสถานะ returned/review และรับผิดชอบการรวมขอบเขตนั้น เพื่อไม่ให้สองฝั่งนำเข้าแพตช์เดียวซ้ำ
2. แตก ZIP ในพื้นที่แยก ตรวจ manifest/ฐาน/รายการเปลี่ยนแปลงและไฟล์ล็อก ห้าม unzip ทับ working tree ปัจจุบันทั้งก้อน
3. ดึงข้อมูล remote ล่าสุด แล้วเทียบ 3 ฝั่ง: ฐานที่ส่งให้แอป, ZIP ที่ส่งกลับ, และ repo ปัจจุบัน รักษา commit งานค้าง เอกสาร และงานของเอเจนต์อื่นที่เพิ่มหลังฐาน ZIP นำเข้าเฉพาะความเปลี่ยนแปลงของแพตช์โดยพิจารณา conflict
4. ตรวจสิ่งที่ผู้ใช้ขอและพฤติกรรมจริง ไม่เชื่อรายงานหรือจำนวนเทสต์อย่างเดียว โดยเฉพาะ NPC ต้องมีเส้นทางตัดสินใจและทำงานจริง เงิน/ทรัพยากรตามบัญชี และเทคโนโลยีไม่ข้ามเงื่อนไข
5. รันการตรวจตามผลกระทบและกฎโครงการ เช่น npm test, npm run check, npm run build, npm run test:browser ใน COMPANY_SOURCE และ benchmark ตามข้อกำหนด แจ้งสิ่งที่รันไม่ได้/พบปัญหา พร้อมสถานะ fixes/review ตามจริง
6. หลังตรวจยืนยัน ให้นำข้อเสนอส่วนที่ทำเสร็จออกจาก ideas แล้วสรุปว่าเกมมีอะไร/ข้อจำกัดอะไรใน project_status_and_ai_onboarding.md ของโครงการ อัปเดตสำเนาที่โครงการใช้งานให้ตรงกันและเก็บรายงานแพตช์เป็นหลักฐาน ส่วนที่ทำบางส่วนให้แยกเฉพาะส่วนที่เหลือไว้ใน ideas ไม่ลบทั้งบทที่ยังมีงานค้าง และแก้ดัชนี/ลิงก์ที่เกี่ยวข้อง
7. commit ให้ขอบเขตชัด ตรวจ remote ก่อน push และไม่ force push ใช้ branch/เป้าหมายตามคำสั่งผู้ใช้ ถ้า main เปลี่ยนระหว่างทำให้รวมการเปลี่ยนแปลงใหม่และตรวจส่วนที่กระทบก่อนส่งขึ้น
8. ลงสถานะ integrated พร้อม commit และข้อจำกัดจริงเมื่อรวมเข้า repo แล้ว ถ้าแค่ตรวจเสร็จแต่ยังไม่รวมให้คง reviewed ไม่อ้างว่างานขึ้น main แล้ว

## ข้อมูลที่ต้องมีในบันทึกงาน

Task ID / เจ้าของงาน / ขอบเขต / base source commit / พรอมต์ / สถานะ / ไฟล์หรือระบบร่วม / ผู้รับช่วงรวมงาน / ไฟล์ส่งกลับ / commit ที่รวม / สิ่งค้าง

ใช้สถานะสั้น ๆ เช่น planned → sent → in_progress → returned → review → fixes → reviewed → integrated หรือ deferred/cancelled ไม่เลื่อนสถานะเองจากแค่เวลาที่ผ่านไป

[AGENT_WORK_STATUS.md](AGENT_WORK_STATUS.md) เป็นทะเบียนงานร่วม ส่วน project_status_and_ai_onboarding.md บอกสิ่งที่เกมมีจริง และ ideas/company เก็บสิ่งที่เสนอหรือยังไม่เสร็จ ทั้งสามไฟล์มีหน้าที่ต่างกันและต้องอัปเดตให้สอดคล้อง
